## 1. 背景与目标

商户、门店、代理、服务商和 Paywizard 运维需要查看终端在计划营业时间内的 Payment Service 在线表现，定位有离线或无数据的终端，并下钻到具体日期、时间段。未创建或启用 Customer Alerts，也必须可以使用本功能。

“在线”仅指终端 Payment Service 与 OPC 的通信情况，不代表 Device Service/TMS 在线、交易必定成功、整机正常或出货成功。离线表示预期通信缺失，不推断网络、设备、供电等故障原因。

本期包括：

- 多终端七天矩阵及历史查询、筛选、排序、分页。
- 单终端详情页中的七天 Service Uptime 摘要及跨页导航。
- 两个入口共用的单日详情、时间轴和明细。
- 门店营业时间、终端继承或完整覆盖、历史版本及授权控制。
- 三分钟心跳、一次漏报容错、连续漏报回溯计离线及一致的统计结果。

本期不包含：修改 Customer Alerts/SLA Alerts 的触发、恢复、Monitoring Hours 或通知逻辑；新增 Device Connection 指标；导出；跨门店批量覆盖；时间表模板库；Special dates；手机浏览器适配。

## 2. 术语与权限

| 术语 | 定义 |
| --- | --- |
| Payment Service | 终端与 OPC 的服务通信通道，本功能唯一统计对象 |
| 有效心跳 | 系统成功接收并认可的 Payment Service 存活上报；终端每 3 分钟发送一次 |
| Online | 按本期心跳判定规则计为在线的时间，包含最终被容忍的一次漏报间隔 |
| Offline | 超过漏报容错后确认的通信缺失区间；从第一次应收到但未收到心跳的时刻回溯计算，直到有效心跳恢复 |
| No data | 当地当天有应统计营业时间，但授权范围内没有任何有效心跳；不计算日在线率 |
| Operating Hours | 按地区时区定义的每周计划营业时间；独立于告警 Monitoring Hours |
| 日在线率 | 当地当天已发生有效营业时间中的 Online 时长占比 |
| Terminal S/N | 物理终端硬件序列号；不同 S/N 的历史不得合并 |
| Terminal Name | 可选业务名称；缺失时不显示名称，不能用 S/N 或占位名称替代 |

查看范围沿用现有终端资源授权。支持无人值守业务的相关 Provider、Agent、Merchant、Store 用户及平台运维可在各自范围内查看；Billing-only、纯 Attended 视角无菜单入口及直接访问能力。

查看历史与管理营业时间是两种权限。管理 Store 计划需对应 Store 管理权限；管理终端覆盖需该终端的当前管理权限。只读用户可以查看授权历史，不可保存配置。具体生产角色与权限点映射由研发评审落实，不依赖前端按钮隐藏或 URL 参数授权。

## 3. 心跳、容错与离线判定

### 3.1 已确认规则

1. 心跳周期固定为 **3 分钟**，不是用户可调参数。
2. **允许一次漏报**：第一次应到的心跳未收到时，暂时保持 Online，不立即扣减在线时长。
3. **第二次仍未收到**：确认连续漏报，Offline 起点回溯到第一次应到但未收到心跳的时刻。不能只从第二次漏报的判定时刻开始扣减。
4. 收到下一次有效心跳时立即恢复 Online；已成立的离线区间结束于该有效心跳时刻。
5. 容错只针对孤立的一次漏报；连续漏报一旦成立，第一次漏报的窗口也必须计入 Offline。
6. 心跳判定在后台持续执行，与页面是否打开、营业时间配置及是否存在告警规则无关。展示时再按日期、营业安排、接入与授权归属区间裁剪。

以下用 `H` 表示最后一次有效心跳的权威时刻，下一次应到时刻为 `H + 3 分钟`，第二次为 `H + 6 分钟`。权威时刻对应的服务端字段与边界并发处理见第 13 节；测试案例均假设接收链路正常、心跳可及时参与判定。

| 时点/条件 | 判定与统计 |
| --- | --- |
| H 至第一次应到时刻 | Online |
| 第一次应到时刻未收到，第二次尚未到 | 处于容错等待，暂计 Online；不新增对外状态 |
| 最迟在第二次应到时刻收到有效心跳 | 仅漏报一次，整个间隔仍计 Online；重启后续心跳判定 |
| 第二次应到时刻仍没有有效心跳 | 确认 Offline，并把起点回溯至第一次应到时刻 |
| 已确认 Offline 后收到有效心跳 R | Offline 区间为 `[H + 3 分钟, R)`，R 起恢复 Online |
| 已确认 Offline 且尚未恢复 | Offline 延续至本次可信统计截止时刻，不能填充未来时间 |

同一时间戳恰好收到第二次应到的有效心跳，应按已收到处理，不生成零长度或瞬时 Offline。区间统一采用左闭右开 `[from, to)`，同一时间不能重复累计。服务端重复收到同一心跳不得创造新的存活证据或延长覆盖。

### 3.2 必须得到一致结果的案例

| 场景 | 结果 |
| --- | --- |
| 08:00、08:03、08:06 正常收到 | 全程 Online |
| 08:00 收到，08:03 漏报，08:06 收到 | 08:00–08:06 全程 Online，无 Offline |
| 08:00 收到，08:03 漏报，在 08:04 查看 | 截至 08:04 暂计 Online；当前结果可能在下一次判定后回溯修正 |
| 08:00 收到，08:03、08:06 都没收到，在 08:06 完成判定 | 08:00–08:03 Online；08:03–08:06 Offline |
| 上例直到 08:09 恢复 | 最终 08:03–08:09 Offline，共 6 分钟；08:09 起 Online |
| 08:00 收到，08:06:30 恢复，期间无心跳 | Offline 为 08:03–08:06:30，共 3 分 30 秒 |
| 08:00、08:06、08:12 分别收到，其间各漏一次 | 两次独立的一次漏报均容忍，不把非连续漏报累计成离线 |

一次漏报的宽限不是永久豁免：第二次漏报确认后，先前暂计的 Online 必须转换为 Offline，日在线率、累计时长、颜色、筛选和排序随同一结果一起修正。前端不轮询；用户下次重新加载取得修正后的快照，当前已展示快照不要求实时跳变。

### 3.3 跨日与精度

心跳判定不在午夜重置。23:57 收到、00:00 漏报、00:03 再次漏报、00:06 恢复，则最终 Offline 为 00:00–00:06。若第一次应到时刻位于前一天，回溯修正必须同时更新涉及的前一天，按当时的营业安排与归属计算。

保留心跳时间戳及推导状态边界的秒级精度，不把真实区间取整到分钟。三分钟心跳只能支持上述推导规则，不能保证识别两次心跳之间所有短暂中断；本期不凭空生成这些中断。

## 4. 日在线率与显示规则

### 4.1 统计范围与资格

每日有效统计范围为以下区间的交集：

`终端当地日期 ∩ 已接入期间 ∩ 当前授权可查看的历史 Store 归属期间 ∩ 当时有效营业时间 ∩ 可信统计截止时刻之前`

当日授权可见、已接入区间内至少有一次实际有效心跳，才具备日在线率统计资格。营业外的有效心跳可以满足资格，但不增加营业内 Online 时长。其他无权查看门店期间的心跳不能为本店当天提供统计资格。

昨天心跳的 Online 覆盖或容错延续到今天，不等于今天收到心跳。后台需要分别保存实际心跳证据和推导的 Online/Offline 区间，不能仅检查当天是否存在 Online 区间来决定资格。

- 当地当天始终零次有效心跳且存在计入营业时间：No data，不输出 0%，不累计为整日 Offline。
- 今天截至快照仍零次心跳且已经营业：同样为 No data。
- 当天随后收到首个有效心跳：当天获得统计资格，按全段已发生有效营业时间重新计算；没有 Online 证据且不属于有效容错覆盖的此前营业区间计 Offline，不只从第一条心跳开始缩短分母。
- 全日休息、尚未营业、接入前、未来日期、无权查看历史各自使用独立状态，不统称 No data。
- 心跳采集链路异常、重复、迟到、冲突等诊断信息保留供研发核查；不新增客户可见的故障原因推断。权威数据如何处理后再供统计使用，必须在接口契约中落实。

### 4.2 公式

当日具备资格且有效统计营业时长大于零时：

`日在线率 = 营业内 Online 时长 ÷ 已发生有效营业时长 × 100%`

`已发生有效营业时长 = Online 时长 + Offline 时长`

Online 使用第 3 节规则的最终或截至快照的暂计区间。Offline 包含连续漏报回溯区间及其他没有有效 Online 覆盖的应统计时间。不得将同一缺口以“漏报”和“离线”两种来源重复累计。营业外和未来时段均不参与分母。

例：08:00–20:00 营业，除 08:03–08:09 离线 6 分钟外均在线，则全天 Online 714 分钟、Offline 6 分钟，日在线率为 `714 / 720 × 100%`，展示 `99.1%`。若只漏 08:03 一次并于 08:06 收到，则该次漏报不扣时长。

### 4.3 状态优先级

先检查接入、保留期、授权归属与当地日期是否可见，再判断有无已发生营业时间，最后判断心跳资格与百分比。不可见历史不能因为后台知道有心跳就对用户显示结果。

| 条件 | 日格 | 可下钻 | 统计处理 |
| --- | --- | --- | --- |
| 接入前且可安全说明接入边界 | Not enrolled | 否 | 无统计 |
| 不在授权归属或保留范围内 | `—`，提示 `No visible history for this date.` | 否 | 不泄露其他门店信息 |
| 终端当地尚未来到该日期 | Upcoming | 否 | 无统计 |
| 没有已发生营业时间，但还有未来营业安排 | Starts at HH:mm | 是 | 无百分比；展示当地下一营业起点 |
| 没有可计入的营业时间且无后续营业安排 | Closed | 是 | 无百分比 |
| 有已发生营业时间，零次有效心跳 | No data | 是 | 无百分比，不计 Offline 累计 |
| 有已发生营业时间且有有效心跳 | 实际在线率与日内时间条 | 是 | 按公式计算，包括合法的 0% |

无可见历史的 `—` 不可下钻。No data、Closed、Starts at 的详情保留可见范围内的营业安排、时区和时间轴，不显示没有意义的两张 0m 统计卡。

例：当天仅营业外收到心跳，营业内没有有效 Online 覆盖，则当天具备统计资格，营业内结果可以是 0%；不能误显示 No data。

### 4.4 百分比、颜色与当天标记

- 按未舍入值分级：≥95% 为绿，≥90% 且 <95% 为黄，<90% 为红。阈值用于运营展示，不是 SLA 承诺。
- 普通百分比向下保留一位小数，整数省略小数。94.999% 展示 94.9%，不能显示为 95%。
- 实际 100% 才展示 100%；非满分但大于 99.95% 时展示 `<100%`。
- 绿色日期仍可含短暂 Offline，详情必须保留，不能因为颜色绿色而删除离线明细。
- 当天且已有计入营业时长，在百分比或 No data 右侧显示时钟图标；提示 `Based on data available at the last update.` 并附当地日期和时区。
- 当天标记只表示当地日历日未结束，不表示实时刷新或故障。营业已结束但日历日未结束，仍可显示。
- 不显示 In progress 文字或额外文字图例，不增加第三行。跨时区终端可在不同日期列显示时钟。
- 已结束日期也可能因连续漏报跨午夜回溯或权威数据纠正而改变；无时钟不代表不可修正。

## 5. 日期、历史与终端归属

1. 默认展示连续七个日期，包含当地今天；日期控件选择截止日后，自动包含前六天。矩阵和摘要都固定保留七格。
2. 单终端摘要及带 S/N 的矩阵以该终端当前有效时区确定截止日；已解绑终端使用最后授权归属的有效时区。跨时区总览以可见范围内最新当地日期作为公共截止日，各行按自己的有效时区判断今天和 Upcoming。
3. 日期控件仅允许历史合法截止日，不能选未来日；接入或可见下限前的前置格仍保留占位，不补造历史。
4. 历史可查询三个日历月；按当地日期向前推三个月，目标月份无对应日则取月末。不得直接等同 90 天。
5. 接入当天只统计权威接入时刻之后的时间；不能把首次告警、首次成功支付或演示样例时间当作真实接入时间。
6. 按当时有效地区时区的自然日归日。跨夜营业按实际日期拆分；夏令时用实际经过时长，不能固定以 24 小时为分母。
7. S/N 为物理终端历史身份。同一逻辑配置换新 S/N，新旧设备各自保留历史；终端名称只作业务展示和搜索。
8. 历史权限取“发生时 Store 归属”与“查看者当前可访问 Store”的交集。原店保留移出前历史，新店不能获得移入前历史；授权上级可查看双方范围。
9. 日中换店，按归属区间切分。解绑不立即删除历史，保留到查询期限；未归属区间不计入任何门店的营业在线率。
10. 换店后默认跟随新店时间表，旧终端覆盖仅用于旧历史，不自动带入新店。
11. 后端可在判定时读取必要的前后心跳上下文，但响应仅返回授权片段，不能泄露其他门店名称或观测明细。

## 6. Uptime Matrix 页面

入口：Device Management → Uptime Matrix，对应 `46.terminal_uptime.html`。

页面标题为 Uptime Matrix，右侧提供 Operating Hours。复用 Portal 侧栏、顶栏、字体、配色和间距，不增加副标题、重复按钮或演示角色切换入口。

### 6.1 筛选和查询

| 控件 | 需求 |
| --- | --- |
| Organization | 仅展示授权范围内组织；支持直接点选、搜索、键盘选择 |
| Store | 随组织联动；上级变化后清除已失效门店，其余有效选择保留 |
| Terminal | 按业务名称或 S/N 搜索；带 S/N 的单终端历史入口固定该终端范围 |
| Show | All terminals / With offline time / With no data |
| Date range | 单日历选择截止日，自动高亮连续七天；允许历史月份，不选未来截止日 |
| Search | 一次提交所有待选条件；终端搜索框 Enter 同效；下拉 Enter 仅选择选项 |

编辑筛选只修改待提交值，不立即刷新结果；组织变化可以立即更新门店候选，但结果等 Search 后统一更新。搜索后返回第一页。无匹配显示明确空态。无 Reset、独立 Refresh 或前后七天工具条。

### 6.2 列表和排序

- 列为 Terminal S/N、Store、连续七个日期。S/N 为蓝色加粗链接，进入对应单终端页并保留授权与只读上下文；名称不得替代 S/N。
- Store 显示所选期间授权可见的归属信息；涉及多个门店时只列当前用户可见门店，详情按实际时间片解释。
- 每页 10 台，显示结果数量与当前范围；首页/末页禁用对应翻页按钮。
- With offline time：所选期间营业内累计 Offline 大于零；容忍的一次漏报不满足条件，连续漏报回溯确认后才满足。
- With no data：所选期间至少一天为 No data。一个终端可以分别匹配两个筛选；Not enrolled、Upcoming、`—` 不等于 No data。
- 默认分组为有 Offline、仅 No data、其他。第一组按营业内累计 Offline 降序，S/N 稳定打破并列。零心跳日不能以整日离线参与排序。
- 无当前心跳但有授权历史的终端继续可见，不因 No data 从 All terminals 中消失。

### 6.3 展示和快照

表头参考 Terminal List：34px 浅灰表头、11px 字体。筛选和主操作 40px，分页按钮 36px。桌面日期格约 48px，两行容纳指标与时间条；时钟不增加高度。长门店名称最多两行并可查看完整提示。

图例与数据更新时间紧凑同排。页面首次打开或重新加载读取最新快照；筛选和翻页使用一致的快照，不因翻页混用不同统计截止时刻。后端实现可采用快照标识或等效机制。保存营业时间成功后更新展示。

前端无自动刷新、轮询或独立 Refresh 按钮。后台持续采集与计算不受此限制。页面请求失败不能解释成终端 Offline。

## 7. 单终端 Service Uptime

位置：`1.terminalmanage_nayax.html` 的 Basic Information，位于 Terminal Transaction Statistics 正上方。无显式 tab 参数时进入 Basic Information，已有 APP/DEX 等深链继续有效。

- 头部包含 Service Uptime、Operating Hours、View history；显示终端有效地区时区与数据更新时间。
- 固定展示最近七个日期格，使用与矩阵一致的指标、颜色、时钟和状态规则。
- 新接入终端不足七天时，接入前日期保留不可点击的 Not enrolled；其他不可见日期按第 4 节占位，不删除格子。

## 8. 单日详情

抽屉显示所选日期、Payment Service、S/N、发生时 Store、当时有效时区、营业安排及日结果。多段计划、时区或归属发生变化时，明细分别保留对应来源，不把当前配置套用整天。

- 有可计算日率时显示 Online、Offline 两项营业内时长；与百分比的分子、分母一致。
- No data、Closed、Starts at 不显示两张无意义的 0m 卡。
- 时间轴保留授权范围内的非营业和未来区间，区分 Online、Offline、No data 与营业外标记。
- 明细列：时间段、Payment Service、是否在营业时间内、持续时长；时间及持续时长支持秒。
- 相邻同类状态仅在营业计划、归属、授权和时区边界均一致时合并；不能跨边界合并后丢失解释依据。
- Previous day / Next day 仅在相邻日期可见时启用，不跳过不可见日期跨越权限或保留边界。
- 矩阵抽屉提供 Operating Hours；摘要抽屉提供带日期的 View history。历史查看权不授予当前终端的配置管理权。
- 关闭按钮、Esc、点击遮罩均关闭；抽屉内部点击、从内部拖动到外部不误关闭。
- 约 240ms 滑入、180ms 滑出并配合遮罩渐变；切日不重新入场，遵循减少动态效果偏好。

## 9. Operating Hours

### 9.1 配置归属和入口

Store 拥有默认周计划及地区时区；Terminal 默认 Follow Store，也可 Custom hours 完整覆盖。Merchant 没有独立继承层。未配置计划时按 24 小时营业，但仍需明确有效地区时区，不能静默使用浏览器时区。

入口为矩阵 Operating Hours、单终端 Service Uptime 的 Operating Hours，以及商户详情中对应 Store 的 Settings。Device Settings 不增加重复入口。

- 矩阵总入口可选 Store/Terminal 维度，通过 Merchant → Store → Terminal 层级点选或搜索对象。
- 详情入口固定当前对象；不存在或无权管理时显示原因，不偷偷切换到其他对象。
- 零终端门店可以配置 Store 计划；Terminal 维度没有候选终端时明确提示并禁止保存。
- Follow Store 展示来源门店和 Effective hours，隐藏周编辑器和可编辑时区。具备门店管理权时可通过 Edit Store hours 明确切换目标。
- 切到 Custom hours 时复制当前有效安排到草稿；完整覆盖周计划与时区，不逐字段继续继承。
- 恢复 Follow Store 后使用门店当前有效计划；旧覆盖版本保留用于历史解释。
- 保存 Store 计划只影响仍跟随该店的终端，不覆盖独立配置；保存区域展示受影响数量。

### 9.2 周计划与交互

- 仅提供 Weekly schedule。星期一至星期日分别设置 24 hours、Closed 或 Custom。
- 周日历按 Monday → Sunday、00:00–24:00 展示。点击星期或时间块，在右侧编辑；允许多个时段和跨夜。
- Effective hours 始终展开，位于周日历上方，按周一至周日显示最终有效时间及地区时区，包含前一天跨夜延续。
- 空白拖选新增、整体拖动、边缘调整采用 15 分钟步长；手工输入保留分钟精度，已有非整刻时间不取整。
- 跨夜时段在相邻两列展示，编辑任一片段修改同一原始时段，并共同高亮。
- Custom 至少包含一个合法时段；结束早于开始表示次日，明确标注 next day。起止相同不允许保存，全天使用 24 hours。
- Start/End 标题只显示一次，输入和删除按钮等高。Add period 仅预填不冲突的后续时段，否则提供待填写行。
- Copy to other days 默认展开；Replace selected days 用当前星期配置替换勾选星期，替换后保持展开并验证跨日冲突。
- 日历计划用低饱和绿色，Closed 用灰色，选择与主操作用黑色；绿色表示计划营业，不表示实时在线。
- 地区时区可点选及搜索，使用 IANA 标识。Follow Store 仅显示继承时区文本。

### 9.3 校验、保存与历史

重叠、重复、空 Custom、非法时间、起止相同均阻止保存；校验包括相邻日及 Sunday → Monday，首尾相接不算重叠。错误指出具体星期和时段，并在实际滚动容器中自动定位、聚焦，避免固定区域遮挡。

周计划中的 Closed 表示当天不新开时段，不取消前一天的合法跨夜延续。若周五 22:00–周六 02:00，周六设 Closed，周六 00:00–02:00 仍计营业；需修改周五时段才能取消。

Save 以服务端生效时刻创建新版本，记录修改人和目标；生效前历史不变，生效后使用新版本。同日中途修改时分段计算。成功关闭编辑器并更新展示；失败保留草稿并说明原因，不伪造成功。Cancel、关闭和 Esc 丢弃未保存草稿，不产生版本或审计；切换对象不得静默保存草稿。

并发保存需校验期望版本；冲突保留输入，提示重新读取当前版本再处理，不能静默覆盖。后台保留版本及审计，界面不增加 Change history。

当前不支持 Special dates。若生产存在真实旧日期例外，需确定统一退役生效时刻并保留旧版本解释历史；如果生产从未上线此能力，不迁移原型演示数据。

所有搜索下拉支持方向键、Enter、Escape、Home、End，候选独立滚动、不被弹窗或底部操作栏裁切，关闭搜索保留已有选择。

## 10. 加载、错误与一致性

| 场景 | 用户应看到的结果 |
| --- | --- |
| 首次加载中 | 明确加载状态，不能先填 0%、100% 或 No data |
| 首次读取失败 | 页面或模块级错误及可执行的重试说明，无伪造结果 |
| 已有结果后查询失败 | 保留仍有权查看的上次成功结果及时间，显示本次失败 |
| 无筛选结果 | 空态，保留筛选输入 |
| 日期或配置非法 | 保留输入和上次结果，定位具体错误 |
| 权限失效 | 清除失去权限的数据和管理能力，不以旧缓存继续暴露 |
| 保存失败或版本冲突 | 保留草稿，错误聚焦可见，不显示保存成功 |
| 心跳数据延迟 | 以可解释的可信截止时间返回结果，标明更新时间；不得把接口故障当成设备离线 |
| 连续漏报触发回溯 | 下一有效快照中同步更新指标、分段、颜色、筛选和排序 |

矩阵汇总与单日明细必须使用同一授权、规则版本和快照语义。数据更新时间表示数据事实，不得仅把页面请求时间作为采集已更新的证明。

## 11. 研发数据与接口职责

本节规定必需信息和行为，不限定接口路径、数据库或任务框架。

| 数据 | 必需内容 |
| --- | --- |
| 终端身份 | 稳定终端标识、物理 S/N、可选名称、终端类型、权威接入时刻 |
| 历史归属 | Store ID、归属起止时刻及组织授权信息；同一物理终端不能存在冲突归属 |
| 原始心跳 | 可去重的事件标识、终端标识、权威心跳时间、接收时间及有效性；区分实际上报与推导状态 |
| 推导状态 | Online/Offline 起止、判定依据、连续漏报确认时刻；离线起点可以早于确认时刻 |
| 计划版本 | Store/Terminal、follow/custom、地区时区、七天时段、服务端生效时间、版本号 |
| 日结果 | 当地日期、可见性原因、是否当天、心跳资格、营业/在线/离线时长、未舍入日率、明细关联 |
| 返回元信息 | 统计截止、数据更新时间、可查询范围、分页总数及快照一致性信息 |
| 审计 | 配置操作者、目标、版本、生效时间；数据纠正应具备可追溯依据 |

接口职责：

1. 查询矩阵：服务端授权、筛选、全量结果排序后分页；七个日期格分别返回状态，不能仅返回有百分比的日期。
2. 查询单终端摘要：使用相同汇总口径返回固定七格及历史入口上下文。
3. 查询单日：返回授权内营业区间、状态分段和计划/归属来源，与汇总一致。
4. 查询和保存 Store 计划、Terminal 继承模式及覆盖计划；校验权限、格式、跨日冲突和并发版本。
5. 后台采集与计算：去重、三分钟节奏、一次漏报容错、第二次漏报回溯、恢复、跨日重算及权威数据纠正。
6. 历史保留：实现三个日历月的可查边界；原始心跳和审计的物理保存期限另行确定，不能误删重算所需上下文。

所有授权在后端执行。前端 `scope`、`access=view`、角色模拟器和 localStorage 不是生产安全机制。心跳计算不得从告警事件数量、成功交易数量或页面打开时间推导。

## 12. 原型与目标需求的差异

| 项目 | 当前原型 | 本期研发目标 |
| --- | --- | --- |
| 心跳来源 | 确定性模拟的有界 online/offline/unknown 区间 | 实际有效心跳证据及本期容错算法 |
| 一次漏报与回溯 | 没有真实心跳判定器 | 3 分钟周期，允许一次漏报，第二次确认后追溯至第一次缺报 |
| 当日心跳资格 | 以存在 Online 区间近似判断 | 依据该日实际有效心跳，不能把昨天覆盖误作今日上报 |

| 配置和权限 | 浏览器本地保存、演示范围 | 服务端版本、审计、并发和真实授权 |
| 原型测试 | 2026-09-18 只读核查时已有 46 项领域测试通过 | 新增真实心跳、回溯和生产接口验收；旧测试通过不代表新规则已实现 |
