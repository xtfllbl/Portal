# 厂商测试卡系统产品需求文档

| 项目 | 内容 |
| --- | --- |
| 版本 | V1.0 |
| 基准日期 | 2026-10-21 |
| 状态 | 研发评审基线 |
| 适用范围 | Paywizard Maintain → Test Cards |

测试卡用于自助机厂商的终端调试与出厂测试。运维发放测试额度，厂商在符合资格的终端上刷卡，消费实际扣减额度并触发出货。厂商无须为此建立生产服务商、商户和门店。

本文按今天最终确认的原型和业务规则整理。“应／必须”为交付要求；静态原型已覆盖的本地交互与生产系统待实现的能力，见第 12 节。

## 1. 背景与目标

正式储值卡服务于商户、门店的生产运营，不能直接表达厂商在终端尚未绑定门店时的出厂测试需求。为测试建立虚构的生产商户、门店，会混淆终端身份、交易归属及经营数据。

本期目标：

1. 运维可统一开卡、批量导入、管理状态、调整测试额度并查询测试交易。
2. 一张测试卡只授权一家厂商，跨厂商不能混用。
3. 终端在首次绑定门店前可进行出厂测试，绑定后结束该资格，解绑不自动恢复。
4. 测试消费真实扣减额度并触发出货，测试卡、测试交易与正式储值卡业务及经营统计隔离。

## 2. 与正式储值卡的差异

本节比较项目现有 Prepaid Cards 业务；正式储值卡的实际充值收款和结算方式继续遵守原业务规则，不由本需求重新定义。

| 比较项 | 厂商测试卡 Test Card | 正式储值卡 Prepaid Card |
| --- | --- | --- |
| 用途 | 终端调试、出厂测试 | 商户、门店的正式运营消费 |
| 管理入口 | Maintain → Test Cards | Portal → Prepaid Cards；Maintain 保留 Card List 及卡详情 |
| 业务归属 | 一家顶层 UPT 厂商 | 服务商下的商户、门店等生产业务范围 |
| 开始使用的前提 | 终端曾进入厂商库存且从未绑定任一门店 | 按原有商户、门店和正式通道规则受理 |
| 当前转给贸易商 | 未绑定过门店时仍可测试 | 按正式终端及生产范围规则处理 |
| 首次绑定门店后 | 立即结束出厂测试资格；以后解绑也不自动恢复 | 进入正式运营，按生产配置受理 |
| 余额含义 | 运维授予的测试额度，无须实际付款；不形成厂商应收或结算款 | 正式储值卡业务余额，按现有生产规则管理 |
| 消费效果 | 实际扣减测试额度并触发出货 | 按原储值卡交易规则处理 |
| 授权范围 | 单选一家厂商，可修改；不配置生产使用范围 | 现有服务商范围内的场景、商户、终端等使用范围配置 |
| 持卡人资料 | 不采集姓名、身份、电话、Email 等资料 | 保留 Card Holder Details |
| 使用限制 | 不提供 Single Use、月限额、日限额及星期／时段配置 | 保留现有单次使用、月／日限额等规则；不据列表静态示例新增时段功能 |
| 卡状态 | Active、Not Active、Suspended、Expired | 保留原状态体系，包括换卡后的 Replaced |
| 激活与到期时间 | 保留；到期时间可不填，不填即长期有效 | 沿用原有效期规则 |
| 单卡／批量开卡 | 均保留；每批统一一家厂商 | 沿用原开卡及导入流程 |
| 余额调整 | 运维增加或扣减测试额度，必须留痕 | 沿用正式储值卡余额管理规则 |
| 丢失换卡 | 本期不提供，无 Replaced 状态 | Portal 保留 Loss & Replacement |
| 交易类型 | 复用储值卡已支持的类型，不额外排除已有退款、冲正；受厂商隔离与原交易规则约束 | 按现有金融交易能力处理 |
| 后台交易页面 | 独立测试交易列表，仅查询；无详情、金融操作及交易导出 | 沿用现有正式 Transactions 及详情流程 |
| 经营数据 | 不进入正式交易记录、营业额及经营统计 | 继续按现有正式交易和统计口径处理 |
| 列表呈现 | 复用储值卡列表样式，移除顶部统计、持卡人、Rule 列 | 保留原页面的统计、字段及交互 |

两套业务可复用卡识别、状态、有效期、余额及已有交易能力，但卡片身份、授权范围、交易归属和统计口径必须明确区分。测试卡不能因终端转入正式运营而自动成为正式储值卡。

## 3. 用户与权限

| 使用方 | 本期职责 |
| --- | --- |
| 有测试卡管理权限的运维人员 | 开卡、编辑、批量导入、卡导出、余额调整及测试交易查询 |
| 厂商测试人员 | 持测试卡在符合资格的终端上测试；不增加厂商自助后台 |
| TMS／终端与交易服务 | 提供终端厂商库存经历、门店绑定经历，执行真实受理和交易处理 |

厂商可选对象仅限顶层 UPT Partner。下级实体即使继承展示 UPT 标签，也不是独立可授权厂商；PSP 及其下级不在选择范围内。厂商选择数据应与 Partner 管理保持一致。

生产系统必须校验运维操作权限，以及卡片、厂商、终端和原交易之间的业务关系。前端过滤、隐藏菜单或禁用按钮不能代替实际授权。本期不新增角色体系或厂商自助审批流程。

## 4. 业务概念与生命周期

### 4.1 核心概念

| 名称 | 定义 |
| --- | --- |
| 测试卡 | 授权一家厂商用于终端调试和出厂测试的 M1 非接触卡 |
| 适用厂商 | 卡片当前唯一获授权的顶层 UPT 厂商 |
| 测试额度 | 卡片可用的测试余额，可由运维增加／扣减，也随受支持交易变化；不代表厂商付款或结算权益 |
| 终端测试资格 | 终端曾进入厂商库存且从未绑定任一门店的资格，与当前持有终端的贸易商分别判断 |
| 终端测试归属厂商 | 终端最近一次进入厂商库存所对应的厂商；普通贸易商之间流转不改变该归属 |
| 测试交易 | 测试卡业务发生的终端交易记录，与正式交易独立查询；手工额度调整属于管理历史 |

术语与根目录 [GLOSSARY.md](../../GLOSSARY.md) 保持一致。

### 4.2 终端测试资格

| 终端经历 | 是否具备资格 | 受理厂商 |
| --- | --- | --- |
| 从未进入厂商库存 | 否 | 无 |
| 进入 A 厂商库存，从未绑定门店 | 是 | A |
| 从 A 流转给贸易商，仍从未绑定门店 | 是 | 仍为 A |
| 在不同贸易商之间流转，仍从未绑定门店 | 是 | 保持最近一次厂商归属 |
| 后来进入 B 厂商库存，仍从未绑定门店 | 是 | 改为 B，仅接受 B 厂商卡 |
| 首次绑定任一门店 | 从绑定起结束 | 不再受理厂商测试卡 |
| 绑定门店后又解绑、退回库存或流转 | 不自动恢复 | 不因重新出现库存关系而恢复 |

当前是否在厂商直属库存、是否仍有 Partner 关系、是否已经解绑，都不能单独证明测试资格。本期不增加手工重新开通测试资格的入口。

### 4.3 卡状态与有效期

| 状态 | 含义及受理要求 |
| --- | --- |
| Active | 有效期条件同时满足时，才可继续校验终端资格、厂商、币种及余额 |
| Not Active | 未激活或尚未到激活时间，不允许消费 |
| Suspended | 已暂停，不允许消费 |
| Expired | 已过期，不允许消费；不以手动选择 Active 绕过已到期时间 |

单卡开卡可选择 Active 或 Not Active；详情保留四种状态管理。设置到期时间时，不得早于激活时间；不填写到期时间则长期有效，但仍受状态、厂商和终端资格约束。恢复状态不恢复终端已结束的测试资格。

## 5. 页面范围与主流程

### 5.1 信息架构

| 入口／页面 | 功能 |
| --- | --- |
| Test Card List | 查询卡、进入详情、新增、Import Cards、Export Cards、余额调整和该卡交易查询 |
| Activation | Single Card 与 Batch Import |
| Card Details | 隶属 Test Card List，包含 General、History、Transactions，不作为独立菜单 |
| Balance Adjustment | 查找测试卡、增加／扣减额度、查看调整记录 |
| Transactions | 独立测试交易查询，与正式 Transactions 分开 |

菜单模块名统一为 **Test Cards**，卡列表名称统一为 **Test Card List**。不提供 Loss & Replacement 或 Transaction Details 页面。

### 5.2 单卡开卡与使用

1. 运维从 Test Card List 点击 Add New Card，或进入 Activation → Single Card。
2. 输入卡 UID、可选显示卡号、币种、初始额度、状态、激活时间和可选到期时间，选择一家适用厂商。
3. 提交后校验卡信息及厂商资格；成功创建卡片并进入详情，记录开卡与初始额度。
4. 厂商在终端刷卡。系统按第 8 节校验，允许的消费实际扣减测试额度并触发出货。
5. 运维通过该卡 Transactions 或独立 Transactions 查询测试结果，通过 History 查看卡管理与余额变化。

## 6. 卡管理需求

### 6.1 卡列表

| 项目 | 要求 |
| --- | --- |
| 筛选 | 卡 UID／显示卡号、适用厂商、状态、余额；当前余额选项为 Zero、Below 10、10 or more，按各卡币种数值筛选，不做币种换算 |
| 列 | UID／显示卡号、适用厂商、余额／币种、状态、最后交易时间、交易次数、操作 |
| 交易口径 | 最后交易时间与交易次数包含该卡成功及失败记录，不作为成功消费次数或营业统计 |
| 操作 | 点击 UID 打开详情；行内提供该卡交易查询、余额调整 |
| 卡导出 | 导出当前筛选结果的全部卡，跨分页；无筛选时导出全部可见卡 |
| 导出字段 | Card UID、Display Card Number、Manufacturer、Currency、Balance、Status、Activation Date、Expiration Date |
| 数量 | 保留底部分页数量，不保留卡列表标题旁 Records 徽标 |

不展示持卡人、联系方式、生产 Group／Store、Rule 列，也不展示 Active Cards、Test Credit、Low Balance、Suspended 等顶部统计。

### 6.2 开卡与详情字段

以下字段约束与当前原型一致。金额上限、支持币种及导入容量在开发评审时应核对正式服务的支持能力，不得无提示截断数据。

| 字段 | 开卡要求 | 详情编辑 |
| --- | --- | --- |
| Card Type | 固定 Test Card | 只读 |
| Physical Type | 固定 Contactless Card (M1 RFID) | 只读 |
| Card UID | 必填；8、14 或 20 位十六进制字符，大小写统一；测试卡内唯一 | 只读 |
| Display Card Number | 可选，最多 60 个字符；填写时测试卡内不区分大小写唯一 | 可编辑 |
| Currency | 必选，一卡一币种；当前原型为 USD、CAD、EUR、GBP | 只读 |
| Initial／Current Balance | 初始额度必填，可为 0；最多两位小数，范围 0～99,999,999.99 | 当前余额只读，通过 Balance Adjustment 调整 |
| Status | 单卡开卡可选 Active、Not Active | 可编辑，按状态与有效期共同生效 |
| Activation Date | 必填，合法日期时间 | 可编辑 |
| Expiration Date | 可选，不早于激活时间；为空代表无到期日 | 可编辑 |
| Applicable Manufacturer | 必选且仅选一家符合条件的顶层 UPT 厂商 | 可编辑 |

不采集 Card Holder Details，不提供 Single Use、Monthly Amount Limit、Daily Amount Limit、生产使用范围或换卡字段。

General 用于编辑；History 展示开卡、资料／厂商变更和余额变化记录；Transactions 展示该卡测试交易，并可带入当前卡条件打开独立测试交易列表。

### 6.3 修改适用厂商

适用厂商允许由 A 改为 B，例如纠正开卡时选错厂商的情况。保存成功后立即按 B 厂商校验，不需要重新发卡；卡 UID、币种和余额保留，显示卡号不会因厂商变更自动重置。

已有交易必须继续归属交易发生时的厂商，不回写为 B。原 A 厂商交易仅可查询，不再允许退款、撤销、冲正等后续操作。修改卡片厂商不改变终端的厂商归属或测试资格。

应保留厂商变更前后对象、操作时间及操作者，支持追溯同一卡片在不同授权阶段的使用情况。

### 6.4 批量导入

1. 进入 Activation → Batch Import，统一选择一家适用厂商。
2. 下载测试卡专用 CSV 模板，填写 Card UID、Display Card Number、Currency、Initial Balance、Status、Activation Date、Expiration Date 七列；厂商由本次导入选择，不逐行填写。
3. 当前原型每文件最多 500 张卡，文件不超过 1 MB。模板不包含持卡人、单次使用、月／日限额或生产范围字段。
4. 上传后逐行预检，展示行号、卡信息、Valid／Invalid 及原因；检查格式、现有卡重复、本批重复、金额、状态、日期及厂商资格。
5. 存在有效行时明确显示本次将导入的有效卡数量，可仅导入有效行，跳过无效行；全部无效时不能提交。成功后明确告知成功数及跳过数，不能把整批提示为全部成功。
6. 提交前再次按最新数据校验；保存冲突或失败不得留下未说明的部分成功结果。修正无效行后可重新上传；已成功导入的卡不能重复创建。

导入和卡导出是两项独立能力，导出文件不要求可直接作为开卡模板重新导入。

## 7. 测试额度管理

从列表行操作或 Balance Adjustment 查找卡片，支持按 UID／显示卡号搜索。运维确认目标卡、厂商、币种和当前余额后，选择 Top-up 或 Deduct，填写金额和备注。

| 规则 | 要求 |
| --- | --- |
| 增加额度 | Top-up 表示授予测试额度，不要求付款，不生成厂商应收或结算款 |
| 扣减额度 | Deduct 表示管理性扣减，不等同于消费、退款或出货 |
| 金额 | 必须大于 0，最多两位小数；操作后余额不得为负或超出余额上限 |
| 备注 | 必填，去除首尾空格后至少 6 个字符 |
| 确认 | 提交前展示卡 UID、厂商、调整类型、金额及调整前后余额；取消不修改余额 |
| 留痕 | 记录时间、类型、调整前后余额、变动金额、币种、操作者及备注 |
| 并发变化 | 余额或卡资料已被其他操作更新时，拒绝按旧余额提交，要求刷新后重新确认 |

额度调整成功后更新卡列表、卡详情和调整历史；不将手工调整写成一笔终端测试消费。

## 8. 终端受理与测试交易

### 8.1 受理条件

消费必须同时满足：

1. 卡片与终端可识别，终端曾进入厂商库存，并且从未绑定过任一门店。
2. 卡片当前适用厂商与终端最近一次厂商归属一致。
3. 卡片处于有效 Active 状态，已到激活时间且未到期。
4. 交易币种与卡币种一致，不通过自动换汇绕过限制。
5. 本次扣减不超过可用测试额度。
6. 涉及原交易的后续操作符合已有交易关联规则，并满足厂商隔离与当前授权约束。

任一条件不满足时拒绝相应操作并返回原因。终端首次绑定门店后，不得因仍持有旧测试配置而继续受理，也不得在正式配置未准备好时回退到厂商测试路径。

### 8.2 交易类型与处理边界

复用现有储值卡已经支持的金融交易类型，包括其原本支持的退款、冲正等，不施加旧版方案中对这些类型的一概排除。具体类型和前置条件以现有交易能力核查结果为准，原型中的 Sale、Refund、Void 示例不是完整承诺清单。

后续交易必须关联正确的原交易，并继续校验卡片授权及厂商关系。卡片改换厂商后，原厂商交易只读；不能通过退款、撤销或冲正突破隔离。

消费成功应按规则扣减额度并触发真实出货。重复请求不得重复扣减；超时、出货失败及补偿处理复用已有储值卡协议中受支持的机制，联调前须核实具体行为，不能把人工增加额度作为交易补偿的默认替代。

### 8.3 交易查询

| 项目 | 要求 |
| --- | --- |
| 查询入口 | Maintain → Test Cards → Transactions；卡列表／卡详情带入该卡查询条件 |
| 筛选 | 日期范围、厂商、卡 UID／显示卡号、终端 S/N、交易类型、交易结果 |
| 列表字段 | 交易时间、交易号、交易发生时的厂商、卡号、终端 S/N、交易类型、金额／币种、交易结果 |
| 结果 | Completed、Failed；成功和失败均可查询，仍在处理中的请求不作为 Pending 交易混入最终记录 |
| 历史归属 | 使用交易发生时的厂商；卡片或终端后续变更不得改写 |
| 排序与数量 | 按交易时间倒序，支持分页并保留交易列表数量 |
| 只读边界 | 交易号为普通文本，无详情页、弹窗或抽屉；不提供后台发起消费、退款、撤销、冲正等操作；本期不提供交易导出 |

后台仅查询不代表终端交易服务禁止已有退款、冲正能力；页面操作范围与受理服务能力分别遵守上述规则。

## 9. 记录、隔离与异常反馈

测试卡、管理历史及测试交易应可独立追溯。操作人使用实际登录身份，不使用演示账号作为生产操作者。测试交易保留发生时的厂商、卡片、终端、金额、币种、类型、结果及必要的原交易关系。

测试卡管理不得读写正式储值卡资料或余额；测试交易不得混入正式 Transactions、营业额和经营统计。不能仅依靠前端页面分流实现隔离。具体部署、存储或交易身份方案由研发评审决定，本 PRD 不要求采用旧版厂商 MID 方案。

| 异常场景 | 产品反馈与处理 |
| --- | --- |
| UID 格式错误、卡号重复、厂商无效 | 阻止提交，说明具体字段及原因，保留输入 |
| 金额、有效期或查询日期范围不合法 | 显示原因及修改方式，不执行变更 |
| 批量导入部分无效 | 在预检中指出行号与原因，仅按明确的有效行数量提交 |
| 目标卡不存在 | 明确提示重新查找已有测试卡，不自动创建替代卡 |
| 余额不足或扣减后为负 | 拒绝操作，保留金额及备注供修正 |
| 其他操作已改变卡资料或余额 | 提示刷新并重新确认，避免覆盖他人的修改 |
| 保存失败 | 展示失败原因及重试方式，保留用户输入，不误报成功 |
| 无查询结果 | 展示空结果状态，保留筛选并允许重置 |

错误提示必须在实际滚动容器内自动定位并获得焦点，不被固定顶栏或底栏遮挡。

## 10. 页面与交互要求

保持现有静态 HTML／CSS／JavaScript 原型架构，执行 [UI 标准](../design/ui-standard.md)。以项目已确认的参考页为本次区域的视觉依据：

- 卡列表对照 Prepaid Cards，复用字体、UID／显示卡号层级、金额／币种双行、状态及行操作；只保留内容面板内一个 Test Card List 标题，新增、导入、导出与标题同行。
- 卡详情对照正式储值卡详情：单一白色面板、内部返回与标题、四格浅灰摘要和原有页签／表单布局。摘要仅为 Card UID、Display Card No.、Current Balance、Status；厂商在表单中呈现。
- Save 位于卡详情右上方，仅在 General 有未保存改动时显示；改回原值、保存完成或切到其他页签时隐藏。不增加固定底部保存区或顶部 Adjust Balance。
- 交易列表对照现有正式 Transactions 的表格及筛选呈现，内容面板内仅保留一个 Transactions 主标题。
- 下拉支持直接点选、输入搜索和键盘操作，选项独立滚动，弹层适应视口；页签支持键盘切换。
- 本期仅验收桌面浏览器。若展示终端名称，应使用可读的业务名称，与明确标注的 S/N 分开；无名称时不以 S/N 或占位名称回填。

## 11. 验收标准

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| TC-01 | 打开 Test Cards 菜单 | 仅有 Test Card List、Activation、Balance Adjustment、Transactions；卡详情隶属列表 |
| TC-02 | 单卡或批量选择厂商 | 仅可选择一家顶层 UPT 厂商，无 PSP、下级代理或继承标签的下级实体 |
| TC-03 | 查看开卡及详情表单 | 保留已确认基础字段，无持卡人、单次使用、月／日限额、生产范围及换卡 |
| TC-04 | 使用重复 UID／显示卡号或错误日期开卡 | 显示原因并定位错误，不保存，不丢失输入 |
| TC-05 | 开卡不填到期时间 | 可保存为长期有效，其他受理约束继续生效 |
| TC-06 | 卡未激活、未到激活时间、暂停或已到期 | 不允许消费；手动 Active 不能覆盖已到期事实 |
| TC-07 | 导入同时包含有效、无效及重复行 | 逐行说明；仅导入明确提示的有效行，报告成功及跳过数量 |
| TC-08 | 筛选后跨分页导出卡 | 导出全部匹配卡，字段完整；不增加测试交易导出 |
| TC-09 | 增加／扣减额度并确认 | 余额与历史同步更新，保留操作者和备注；取消确认不发生变更 |
| TC-10 | 调额为零、备注不足或扣减超余额 | 拒绝并显示原因；不产生余额变动 |
| TC-11 | 调额确认前余额已被其他操作改变 | 拒绝使用旧余额提交，刷新后重新确认 |
| TC-12 | A 卡在归属 A、从未绑定门店的终端消费 | 其他条件满足时成功扣减测试额度并触发出货 |
| TC-13 | 该终端转给贸易商或在贸易商间流转 | 从未绑定门店时继续接受 A 卡 |
| TC-14 | 该终端后来进入 B 厂商库存 | 仅接受 B 卡，拒绝 A 卡；不改写历史交易归属 |
| TC-15 | 终端首次绑定任一门店后再次测试 | 立即拒绝；后续解绑、退库或流转不自动恢复资格 |
| TC-16 | 币种不符、跨厂商或消费余额不足 | 拒绝操作并返回原因 |
| TC-17 | 卡片适用厂商从 A 改为 B | 保存后按 B 受理，保留 UID、币种和余额；A 历史仍归 A，且后续金融操作被拒绝 |
| TC-18 | 查询测试交易及卡内交易 | 可筛选成功／失败记录，只显示最终结果；交易号无详情入口，无金融操作 |
| TC-19 | 查看正式卡、正式交易及经营统计 | 不出现测试卡业务数据；正式业务原有流程正常 |
| TC-20 | 重复消费请求、超时或出货异常联调 | 不重复扣减；按核实后的原交易及补偿规则处理并可追溯 |
| TC-21 | 桌面对照卡列表、详情及交易页 | 单标题、无卡统计／Records 徽标、详情结构和 Save 显隐符合本期基线；下拉及错误定位可用 |

## 12. 交付边界与研发评审事项

当前静态原型覆盖五个页面及浏览器本地卡管理、批量导入、卡导出、额度调整和演示交易查询。已有桌面验证记录见 [Test Cards 实施与验证](../validation/test-card/README.md)。这些记录不构成真实扣款出货、TMS 同步或服务端授权验收。

| 研发评审事项 | 需要明确的交付结果 |
| --- | --- |
| 终端资格数据 | 如何取得完整厂商库存经历、最近一次厂商归属及首次门店绑定事实；历史数据不足时的处理策略须在联调前明确 |
| 正式绑定生效边界 | 绑定与测试请求并发时如何保证资格立即终止；终端旧配置不能继续受理 |
| 已有交易能力 | 核实储值卡实际支持的交易类型、关联条件、重复请求、超时、出货失败及补偿行为，形成联调清单 |
| 授权切换 | 厂商修改与并发交易的生效顺序，以及历史原交易操作限制的实现；不能只比较当前厂商名称 |
| 卡身份与数据隔离 | 明确测试／正式卡识别方式，同一物理卡 UID 的两套业务冲突策略，以及查询、统计和存储隔离方案 |
| 数据口径 | 确认金额上限、币种、时间及时区、导入容量与正式服务能力一致 |
| 权限与审计 | 复用现有运维权限并覆盖全部接口，记录真实操作者；核对批量和导出不能绕过权限 |

上述事项用于补齐生产交付方案，不改变本期已确认的产品范围。本期不增加厂商自助门户、丢失换卡、交易详情、后台金融操作、测试交易导出、顶部统计或自助恢复终端测试资格。
