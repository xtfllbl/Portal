# Billing 产品需求文档

版本：1.1 · 日期：2026-09-09 · 状态：演示原型已按确认口径开发，验证记录见第17节。

本 PRD 覆盖 Billing Setup、Billing & Payments、公开付款页、Billing Overview 及相关邮件。按当前 HTML、页面脚本和领域文档核查；本次确认的新规则优先于历史原型行为。用户已进一步确认本次只开发演示原型；真实支付渠道、邮件实投、生产鉴权和真实政策文件不属于本次交付。

## 1. 范围与确认结论

| 页面 | 文件 | 使用者 | 职责 |
| --- | --- | --- | --- |
| 41 · Billing Setup | [41.billing_setup.html](../../41.billing_setup.html) | WizarPOS Provider 运营人员 | 创建账单、保存和编辑草稿 |
| 42 · Billing & Payments | [42.billing_payments.html](../../42.billing_payments.html) | 商户用户 | 查看本商户账单、首次付款、授权、手动补扣、导出历史 |
| 43 · Public Billing Payment Page | [43.billing_payment_link.html](../../43.billing_payment_link.html) | 持有该账单链接的付款人 | 无需门户登录完成首次付款；首次成功后只读查看状态和记录 |
| 44 · Billing Overview | [44.billing_overview.html](../../44.billing_overview.html) | WizarPOS Provider 运营人员 | 管理已签发账单、复制或发送链接、续期、查看记录、停止收款、导出 |

本次确认的核心规则：

1. 分期失败后，到下一个正常分期扣款日自动从最早未付期补扣，逐笔成功后继续，直到当期；任何一期失败立即停止本轮。
2. 自动扣款时间为正常到期日 **09:00 UTC**。账期间不额外自动重试；平台可以人工 Retry Payment；用户端不提供重试或换卡。
3. 同一期自动与手动扣款互斥；当天手动扣款失败后，该账单当天不再发起自动扣款。已成功期永不重复扣。
4. 最后一个计划扣款日之后，不再新增自动扣款日期；欠款保留，只能平台人工逐期补齐。合同不延期、不续订、不增加期数。
5. 邮件包含现有付款邀请、每笔成功收据，以及新增的实际扣款失败通知。未授权账单仅因逾期不发提醒邮件，不增加每日催付、扣款前提醒或停止收款通知。
6. 本次交付为演示原型：“下期自动补扣”、按事件保存成功/失败邮件快照、44查看邮件及演示政策弹窗已实现。默认仍为浏览器本地演示；不会真实扣款或寄信。

不在本期范围：无限续订、改卡、运营代点扣款、拆分单期金额、跳过旧期支付新期、提前结清未来期、退款/冲正操作界面、停止后恢复原账单、合同金额或期数变更、优惠券、税费计算、换汇、真实邮件模板视觉制作。

## 2. 术语与金额口径

术语以 [CONTEXT.md](../../CONTEXT.md) 为准。

| 术语 | 定义及使用约束 |
| --- | --- |
| Billing Record / 账单 | 一笔可一次性或固定月付收取的义务；一个链接对应同一个账单，不是每次打开新建账单 |
| Merchant Billing | 归属指定商户的账单；商户门户与公开链接支付同一笔义务 |
| Standalone Billing | 不归属商户的独立账单；由运营管理，经公开链接支付，不出现在商户账单列表 |
| Fixed-term Billing Contract | 固定每月金额、固定期数的合同；全部约定期数支付完成后停止 |
| Contract Installment / 期 | 独立的期号、计划到期日、金额与结算结果；欠款不得合并成一笔扣款 |
| Payment Attempt / 扣款尝试 | 针对一期的一次实际尝试；一期可有多次失败，最多结算成功一次 |
| Collection round / 本轮扣款 | 一次首次付款、计划扣款或手动重试触发的逐期执行过程；遇到失败或结果未明确立即停止继续提交 |
| Installment Catch-up Collection / 逐期补扣 | 从最早到期未付期开始，逐笔扣至当期，失败即停 |
| Recurring Payment Authorization | 付款人允许保存付款方式并收取剩余固定期款项的明确授权；授权成功不等于付款成功 |
| Billing Link Recipient | 运营 Send Link 指定的邀请收件人；邮箱不改变账单归属 |
| Payer email / 付款邮箱 | 首次 checkout 填写的邮箱；成功收据和失败通知使用该邮箱，后续分期使用授权保存的邮箱 |
| Collection Stop | 永久停止新收款；不退款、不免债、不把未付标为已付 |
| Link Renewal | 延长同一个链接有效期；不改变合同时间、期数、进度和 URL |

| 金额/日期 | 规则 |
| --- | --- |
| 单期金额 | 分期的 Base Monthly Fee；一次性账单的全部应付金额 |
| 合同总额 | 单期金额 × 总期数；一次性总额等于单期金额 |
| 累计已付金额 | 只累计已结算成功的期金额；失败金额和重复回调不计入 |
| 全部未付金额 | 合同总额减累计已付金额，包含逾期、当期及未来期；Stop 弹窗显示该口径 |
| 本轮应付总额 | 本轮将尝试的到期未付期金额合计；用于确认展示，实际仍分期逐笔扣款 |
| 本次实付金额 | 某一次成功支付的金额；每封成功收据使用此数，不能用本轮合计或合同总额替代 |
| 最早未付期日期 | Next Payment 当前原型字段的主要含义；有欠款时可能是过去日期，不能将其当作下一次自动执行时刻 |
| 下一自动执行时间 | 尚未到来的正常计划扣款日 09:00 UTC；无后续计划日、全付或停止时为空 |
| Billing Period | 当前页面显示原始 Billing Start Date 至开始日增加N个月的期间终点；N为总期数；不是按实付日重新计算，也不是最后一期扣款日 |
| 历史表 Period Ends（原Due Date） | 42/44已将原Due Date列改名Period Ends，实际取期间终点（开始日+N个月），最后一期计划扣款日则是开始日+(N−1)个月；该列不能作为扣款任务依据，也不是最早欠款期到期日 |

金额按币种最小单位精确计算；本期 USD/CAD/EUR 均保留两位小数。改变 Currency 只指定计价币种，不执行汇率换算。

## 4. 状态模型与操作资格

### 4.1 收款状态

| 状态 | 判定 | 可发生的后续变化 |
| --- | --- | --- |
| Draft | 未签发的配置，无可支付发票/链接/分期计划 | 编辑后保存，或签发 |
| Pending | 已签发、未付款/未授权，尚无失败及分期逾期 | 首次支付、授权、Overdue、Stopped |
| Active | 已授权、有剩余期数，当前无欠款失败 | 后续自动扣款；失败或形成欠款变 Overdue；付清变 Paid；运营停止 |
| Overdue | 扣款失败即进入；分期存在到期日早于当前 UTC 日期的未付期也进入 | 首次付款或补扣；当期以前清零且有未来期变 Active；全部付清变 Paid；停止 |
| Paid | 所有约定期均已付清 | 仅查看；不再扣款、续期或停止 |
| Stopped | 运营永久停止收款 | 保持停止；已提交交易的迟到结果可更新历史与金额，但不得重新启用收款 |

状态优先级：Stopped 优先，其次 Draft、Paid，再判断 Overdue、Active、Pending。单期 Failed 不应使未尝试的后续期也变成 Failed。单期明细保持 Pending / Failed / Paid；停止账单中未付期显示 `Stopped · Unpaid`。

一次性账单当前不会仅因“创建日已过去”自动变为 Overdue；实际扣款失败才进入 Overdue。分期未授权也可能因原计划日已过而 Overdue，但本期不因此发送催付邮件。

### 4.2 链接状态

| 状态 | 判定 | 页面行为 |
| --- | --- | --- |
| Valid | 未使用、未停止，且未超过有效期 | 可首次付款、授权、Send Link |
| Expired | 未使用，当前 UTC 日期大于 expiry | 阻止首次付款/授权；可由运营 Renew |
| Used | 已授权、已有成功付款或已经付清 | 只允许看结果；禁止用户Retry、换卡及重复首次付款/授权 |
| Disabled | Draft 或 Stopped | 不提供新的付款入口；Stopped 原链接显示停止结果 |

有效期当天截至 UTC 日末仍有效，次日开始过期。已授权链接显示 Used，即使原 expiry 已过也不撤销授权，不阻止正常自动扣款或平台 Retry。收款状态与链接状态独立，例如 `Overdue + Used`、`Pending + Expired`。

### 4.3 操作资格矩阵

| 条件 | Pay Now / 首次 Pay | Retry Payment（仅平台44） | Send Link | Renew Link | Stop Collection |
| --- | --- | --- | --- | --- | --- |
| Draft | 否 | 否 | 否 | 否 | 否 |
| 未授权、未付、Valid | 是 | 否 | 是 | 否 | 是 |
| 未授权、未付、Expired | 否 | 否 | 否 | 是 | 是 |
| 已授权、正常 Active | 否 | 否 | 否 | 否 | 是 |
| 已授权、Overdue、有到期未付期 | 否 | 是 | 否 | 否 | 是 |
| 已付清 | 否 | 否 | 否 | 否 | 否 |
| 已停止 | 否 | 否 | 否 | 否 | 否 |

Copy URL / Preview 对已签发账单可用，包括 Paid、Stopped；它们只打开对应结果，不能绕过状态校验。金额、资格和期数必须在提交时重新校验，不能只依据打开页面时的快照。

## 6. 42 · Billing & Payments

### 6.1 列表与字段

Pending Payments 仅展示本商户需要首次付款的账单。首次成功后的已授权账单（含Overdue）在历史中查看状态，由系统自动扣款或平台人工补扣。未授权过期账单保留卡片但 Pay Now 禁用。首次成功后的Active、Overdue、Paid和Stopped均不提供用户待付款操作。未选择商户显示引导空态。

卡片显示单期金额、Invoice、链接到期日、备注、Billing Amount、总期数和 Recurring On (Fixed-term)/Off。单期金额不是本轮欠款合计，真正提交前须展示逐期应付清单。

Billing History 一账单一行，包含全部非Draft状态；不是仅成功交易流水。列包括发票、UTC创建时间、商户、合同期间、周期、合同总额、收款状态、已付期数、Period Ends（期间终点）、链接过期日、授权状态、最早未付期日期及下一自动尝试UTC时间。当前没有分页和行操作。

## 10. 分期支付、逾期与补扣引擎

### 10.1 日期与首次付款

计划第i期日期 = Billing Start Date 按原始日号增加i−1个月。例如1月10日开始的6期合同，最后一期扣款日为6月10日；42/44期间终点Period Ends显示7月10日，7月10日不得新增第7期或自动追扣。短月取当月最后一天，下个月仍恢复原日号，例如1月31日→2月28日→3月31日，不漂移至3月28日。

首期在首次付款确认后立即收，即使开始日在未来。首次付款较晚时，第一期和所有当前已到期未付期都进入本轮；其他未来期不收。每月一期，最多到合同总期数。首次授权说明要覆盖本次清单、保存卡、后续自动按计划收取及到期补扣规则，不使用无限订阅文案。

### 10.2 自动收款

1. 正常后续期到期日09:00 UTC，针对已授权、未停止、未全付合同创建一轮计划收款。
2. 检查该计划日是否已处理、当天是否已有手动失败、是否有在途尝试；不符合则不新发扣款。
3. 读取当前到期未付期，按期号升序排列。第2期失败时，下期不是直接扣第3期，必须第2→第3；失败不能永久阻塞以后正常计划日。
4. 每次只向支付渠道提交一期金额；成功记该期Paid和一条成功记录，再继续下一期。每一期均有自己的支付ID。
5. 明确失败：记失败尝试、该期Failed、账单Overdue，停止本轮；未提交期保持原状态；发一封本轮失败通知。
6. 结果未知/处理中：暂停本轮，等待查询或回调确认，不将其当失败重新扣，也不继续新一期。
7. 当期及以前清零且有未来期：Active；所有期结清：Paid；存在未付到期期：Overdue。处理过程中尊重Stopped优先级。

不能把“刷新页面”作为生产扣款触发器。调度重复触发必须幂等；服务故障后恢复应补处理同一个遗漏计划任务，使用同一业务标识，不新增扣款日期或扩大本轮应付范围。计划任务已在期末创建但结果未明的，期末后可完成结果核对；这不等于新增期末后自动追扣。

### 10.3 手动补扣与同日冲突

手动Retry经过第8节明确确认，仍旧期优先、每期独立、失败即停。自动与手动共用账单级执行互斥和单期结算去重；44多个标签页同时提交，也只能一轮生效。

当天手动失败后禁止该账单当天任何新的自动尝试；平台再次明确发起手动Retry仍可执行，但不得与在途支付并发。自动已成功期在后续手动列表排除。手动已结清当前期后，当天自动任务读取不到应付期则直接结束。自动任务已在途时，手动入口提示正在处理，不额外提交。

确认清单与提交时清单不一致时要求重新确认，不能静默扣更多金额。若第2期已由别处付清，旧确认不得再扣第2期。支付请求超时后先以原标识查明结果；“刷新”和“重试网络请求”不得变成新业务扣款。

### 10.4 合同期末与停止

最后计划日仍执行正常的旧期至最后一期补扣；失败后保留欠款。以后没有新的计划扣款日，也没有每月自动追扣；平台人工Retry可清到最后一期。全付后无Next payment，无再次扣款。Stop优先于所有资格，下一期到来也不再启动。

| 开始日在未来 | 12月20日首次确认1月10日开始的合同 | 立即只扣第1；第2仍为2月10日，不在1月10日重复扣第1 |
| 迟付或续期后首次付 | 3月15日首次确认 | 展示1/2/3各USD100合计USD300，逐笔执行；第4仍为4月10日 |
| 最后日仍失败 | 6月10日从第5补起，第5失败 | 不尝试6；7月10日不自动；后续手动5→6全部成功才Paid |
| 短月 | 1月31日开始 | 第2到期2月28日，第3到期3月31日；付款迟到不改锚点 |
| 链接已过期但已授权 | expiry已过，存在欠款 | 链接Used，保留Retry及下一正常日自动，不Renew |
| 已停止时晚到成功 | 运营Stop后，之前已提交第2期回调成功 | 更新第2期和收据，账单仍Stopped，不启动第3期 |

### 11.4 支付成功收据 · Payment receipt

建议主题：`Payment receipt — {invoiceNumber}`。每封对应一笔成功，不为失败生成成功收据。补扣2→3→4全部成功时生成3封，各自显示USD100和自己的期号，不能生成一封“USD300，第4期”替代。

| --- | --- |
| paymentStatus | 必须Succeeded，否则拒绝渲染成功收据 |
| invoiceNumber / paymentReference | 对应账单与成功支付唯一标识；用于追踪、去重；现有renderer未将paymentReference显示为独立行，投递实现仍须携带 |
