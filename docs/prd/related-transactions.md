# 关联交易 PRD

日期：2026-09-17  
适用页面：`12.transaction_list.html`，以及从关联记录进入的 `11.transaction_detail_redesign.html`  
阅读对象：产品、研发、测试

本文按当前已确认的设计整理，说明正式产品要达到什么效果。页面目前使用演示数据，能够演示交互，不代表真实关联查询、服务端权限和历史数据已经具备。还需要研发核实的事项放在第 12 节。

## 1. 为什么要做关联交易

用户查到一笔退款时，通常还想知道：这笔退款对应哪笔消费？之前有没有退过？有没有失败的退款？如果前面做过预授权，实际退的是哪笔授权完成交易？

只看当前这一行，很难把这些事情弄清楚。用户需要反复找交易、比金额、记 ID，而且很容易把没有关系的记录看成同一笔业务。

关联交易要解决的就是这个问题：用户找到其中任意一笔，就能顺着明确的支付关系看到前后发生了什么，必要时再打开某一笔的详情。主列表继续一行显示一笔交易，不把几笔流水合成一行。

做到下面三点，这个功能才算对用户有用：

- 找得到：在当前交易上就能打开关联记录，不用先找到原始消费。
- 看得懂：知道自己从哪笔进来、每笔是什么操作、结果如何、直接针对哪笔交易。
- 回得去：查完详情返回列表，仍在之前的 Tab、筛选条件和位置上。

## 2. 这次写到哪里

本次覆盖列表中的 Related Transactions 入口、关联弹窗、详情页关联表、关联记录之间的跳转，以及返回列表的行为。也说明分页、空状态、加载失败、关系不完整和权限限制的要求。

关联表是查看入口。退款、撤销、预授权完成等操作仍走原有流程，本次不在关联表里增加这些操作按钮，也不改变通道原有的操作能力、金额限制或小票规则。

首版不增加整组交易的金额汇总，不新增零售或餐饮订单管理，也不新增“导出整组关联交易”。只要求桌面浏览器使用，不做手机适配。

## 3. 什么算“关联”

### 3.1 必须有明确的支付引用

例如，一笔退款明确指向某笔消费，两笔就可以建立关系；一笔撤销明确指向某笔授权完成交易，也可以建立关系。

不能因为两笔交易用了同一张卡、金额相同、时间接近，或者外部订单号相同，就把它们放在一起。RRN 相同也不能单独作为关联依据。这里查看的是支付交易之间的关系，不按商家的零售订单归组。

当前原型在同一 MID、同一支付通道的范围内匹配明确引用。正式接入时需要核实实际支付账户的隔离范围，不能把一个通道或商户账户里的编号拿到另一个范围匹配。

终端相同不是必要条件。原消费和后续退款如果在不同终端执行，只要支付关系可信、账户范围符合要求，而且用户有权查看，两笔仍应出现在同一组里。

### 3.2 从任何一笔进入，都要能看见同一过程

假设消费 S 后面有两笔退款 R1、R2。从 R2 打开关联交易时，要能看到 S、R1、R2，不能只看到 R2 和它直接对应的 S。

如果 R1 后面又发生了明确针对它的撤销，这笔撤销也属于这个支付过程。在同样的权限和数据完整程度下，从组内任意一笔进入，组内成员应一致；改变的是 Current 标记。

这里的“完整”始终受用户权限和实际已取得的数据限制。有历史缺口时要说明，不能保证没查到的记录就不存在。

### 3.3 三个容易混淆的概念

| 页面用词 | 用通俗的话解释 | 例子 |
| --- | --- | --- |
| Current | 这次打开时选中的那笔交易 | 从退款 R 打开，R 就是当前笔 |
| Original Transaction | 这一支付过程最开始的消费或预授权 | 先预授权 A，再完成 C，再退款 R，最初交易是 A |
| Applies To | 这一行的操作直接针对哪一笔 | R 退的是 C，所以 R 的 Applies To 是 C |

Original Transaction 和 Applies To 可能是同一笔，也可能不是。尤其不能把表格里时间上排在前一行的交易，自动当成下一行的作用对象。

### 3.4 哪些类型和结果会出现

覆盖现有支持的、有明确支付关联的交易记录，包括消费、退款、部分退款、撤销、预授权、预授权增加、预授权完成和小费调整等。出现在这份范围里，表示支持查看其记录，不表示所有支付通道都支持执行该操作。

交易类型和交易结果分别展示。退款失败了，Type 仍然是 Refund，Result 是 Failed；不能把 Type 也改成 Failed。

平台交易记录只保存 Completed、Failed 两种最终结果。关联区同样只展示这两种结果，不出现 Pending，也不把仍在处理的请求临时凑成一笔交易记录。

## 4. 用户从列表怎么打开

用户先在 Transactions 找到一笔交易，再点击该行 Actions，选择 Related Transactions。

每笔交易都有这个入口，不要求用户先知道它有没有关联，也不要求列表先查出关联数量。点击后关闭 Actions 菜单，打开居中的 Related Transactions 弹窗。

主列表不增加独立的关联列或数量按钮。Transaction Details、Send Receipt、Terminal Details 等现有入口保留各自的用途和可用条件。

弹窗应支持三种关闭方式：右上角关闭按钮、Esc、点击弹窗外遮罩。点击弹窗内部、选中文字或在表格中滚动，不应误关弹窗。关闭后焦点回到原来那行的 Actions 按钮，列表保持原样。

## 5. 弹窗里具体展示什么

### 5.1 顶部信息

有多笔关联记录时，内容区上方展示总笔数；能确认最初交易时，同时展示 Original Transaction 及其 Transaction ID。

总笔数包含当前笔。例如消费加两笔退款，应显示 3 transactions，不是 2。这个数表示当前用户有权查看的关联记录总数，不能用主列表当前页的条数代替，也不能把权限外的记录算进去。

无法确认最初交易时，不随便挑时间最早的一笔来填 Original Transaction。已知数据不完整的处理见第 9 节。

### 5.2 关联表字段

| 字段 | 用户看到什么 | 具体要求 |
| --- | --- | --- |
| Time (UTC) | 该笔交易的处理时间 | 首版沿用 UTC 列头。同一张表统一时区，不能直接拼接不同终端的本地时间 |
| Type | Purchase、Refund、Auth Completion 等交易类型 | 显示这笔交易本身的类型，不根据 ID 前缀或结果猜测 |
| Amount | 币种和该笔金额，例如 GBP 12.40 | 使用这笔记录自己的金额、币种和金额含义，不求和、不换算出新的汇总金额 |
| Result | Completed 或 Failed | 用文字和对应状态颜色一起表达，不能只靠颜色 |
| Applies To | 本笔操作直接针对的交易 ID | 可查看的对象提供链接；本来没有直接对象时显示 `—`；有引用但对象不可用时按第 9 节处理 |
| Transaction ID | 该笔交易的对外展示编号 | 当前笔显示普通文本，其他可查看的交易提供详情链接 |

每条记录只展示一个 Transaction ID。编号可能是纯数字，也可能带字母，页面不能从编号的长度、前缀推断交易类型。内部查询用的记录键不展示成 Transaction ID，加载提示和错误提示也必须遵守这一点。

长 ID 可以换行，用户可以选中文字复制。首版没有额外的一键复制按钮，不为此增加新的操作列。

### 5.3 当前笔、排序和分页

当前笔用整行浅蓝底色标出，并在 Type 旁显示 Current。用户打开弹窗后，应直接落在当前笔所在的页，并能看见这一行，不必从第一条翻找。

表格按处理时间从早到晚排列；时间相同时沿用 Transaction ID 的稳定排序。同一份结果反复查看时，不应无故变换顺序。

每页 10 条。超过 10 条时显示当前范围、总数，以及 Previous、Next、Locate current。Locate current 的作用是回到当前笔所在页并定位该行，不改变当前交易。第一页的 Previous 和最后一页的 Next 不可用；不超过 10 条时不显示分页控件。

关联表使用 34px 浅灰表头、11px 字体，沿用 Portal 的字体、按钮和配色。表格在自己的区域内滚动，表头保持可见，长内容不应把弹窗撑出桌面视口。

### 5.4 为什么不显示合计金额

关联记录里的金额不一定能直接加减。例如，预授权金额、预授权增加金额、完成金额分别描述不同操作；失败退款有一个请求金额，也不代表这笔钱已经退成功。

因此本期只展示每笔自己的金额、币种、类型和结果。不增加“总支付”“总退款”“剩余可退”“净收款”等整组金额，也不把不同币种折算后相加。

后续交易操作原有的额度判断继续使用自己的规则。不能因为关联查看加入了失败记录，就让失败退款占用原流程的可退额度。

## 6. 点击关联交易后怎么走

### 6.1 在当前标签页打开对应详情

点击其他记录的 Transaction ID、可访问的 Applies To 或 Original Transaction 链接，在当前浏览器标签页进入目标交易详情。当前笔自己的 ID 不提供重复跳转。

进入目标详情后，页面展示顶部，并短暂显示 `Now viewing transaction …` 提示，带出目标 Transaction ID。提示约 3 秒后自动收起，不挤动页面内容。

这里按最新原型行为处理：打开目标详情顶部，先让用户确认自己正在看哪笔交易。

### 6.2 整个详情必须一起切换

不能只把关联表里的 Current 换一下，顶部仍保留上一笔的金额。切换交易后，以下内容都要对应目标笔：

- Transaction ID、金额、币种、交易类型和结果。
- 商户、终端和该笔实际返回的详情字段。
- 关联表中的 Current 标记。
- View Receipt、Send Receipt 对应的小票对象和可用状态。

目标笔没有某个详情字段时，按原详情页的空值规则处理，不能借用上一笔的数据。目标笔没有可用小票时，相关入口不可用，也不能打开上一笔小票。

详情里的关联表放在当前笔摘要下方、详细字段上方，与列表弹窗使用同一套关系和展示规则。在相同数据、权限条件下，两处的成员、金额、结果、直接关系和总数必须一致。

刷新目标详情或直接打开它的地址，仍应加载地址对应的交易。交易不存在或已不可访问时，显示交易不可用并提供返回 Transactions 的入口，不能回到一笔固定的演示交易。

### 6.3 查完以后返回列表

从列表进入详情，再点击 Back，应恢复进入前的列表上下文，包括：

- Completed 或 Failed Tab。
- 已应用的筛选条件、日期范围和筛选面板展开状态。
- 页码、每页条数。
- 列表横向滚动位置、表格及页面纵向位置。

从一笔详情继续跳到另一笔关联详情后，再点 Back，仍回到最初进入时的列表上下文。返回时不自动重新打开关联弹窗。

如果用户是直接打开详情地址，没有此前的列表上下文，Back 返回普通 Transactions 入口即可。

## 7. 关联结果与列表筛选是什么关系

列表筛选帮助用户找到入口交易；关联查询负责把这笔交易的支付过程展示出来。这两件事的查询范围不同。

例如，消费 S 成功，第一次退款 R1 失败，第二次退款 R2 成功：

| 查看位置 | 应该出现的记录 |
| --- | --- |
| Completed 列表，且符合其他筛选条件 | S、R2 |
| Failed 列表，且符合其他筛选条件 | R1 |
| 从 S 打开关联交易 | S、R1、R2，S 标记 Current |
| 从 R1 打开关联交易 | S、R1、R2，R1 标记 Current |
| 从 R2 打开关联交易 | S、R1、R2，R2 标记 Current |

所以，关联查询不继承主列表的成功／失败 Tab、日期、类型、金额等过滤条件，也不受主列表分页限制，但始终继承当前用户的数据权限。

如果用户筛选今天，查到今天的退款，而原消费发生在昨天，关联区仍要能显示那笔可见的原消费。主列表不因此多出昨天的记录。

打开关联交易不会改变主列表的计数、分页和导出范围。用户在原列表导出时，仍按原有筛选和导出规则执行，不自动带出整组关联记录。

## 8. 用四个例子把规则说清楚

以下金额和交易 ID 来自当前原型，供评审和测试定位使用。它们是演示记录，不是对真实通道能力的说明。

### 8.1 一笔消费，两次部分退款

| 交易 ID | 类型 | 金额 | 结果 | Applies To |
| --- | --- | --- | --- | --- |
| 84607420342 | Purchase | GBP 48.60 | Completed | — |
| 84607420357 | Refund | GBP 12.40 | Completed | 84607420342 |
| 84607420361 | Refund | GBP 5.00 | Completed | 84607420342 |

从第二次退款打开，也要看到全部三笔。两笔退款都指向原消费，第二次退款不指向第一次退款。顶部 Original Transaction 是 84607420342，总数是 3。

用户能看到每次各退了多少，但本期不额外计算累计退款或剩余金额。

### 8.2 有一笔失败退款

原型中消费 `PT20260916001834` 为 USD 3.50，关联一次 USD 1.00 的小费调整、一次 USD 1.00 的失败退款，以及一次 USD 0.50 的成功退款，共四笔。

从 Failed Tab 中那笔失败退款打开，应看到全部四笔。失败退款这一行显示 Refund 和 Failed，不因为失败就隐藏，也不能显示成已退款成功。四笔分别保留自己的金额。

成功退款是另一笔交易记录，不覆盖前面的失败记录。用户由此可以看清先后发生了哪些操作。

### 8.3 预授权、增加、完成，再退款

| 简称 | 交易 ID | 类型 | 金额 | 直接作用于 |
| --- | --- | --- | --- | --- |
| A | 84607420410 | Pre-Authorization | USD 180.00 | — |
| I | 84607420421 | Incremental Authorization | USD 45.00 | A |
| C | 84607420437 | Auth Completion | USD 212.50 | A |
| R | 84607420502 | Refund | USD 32.50 | C |

从 R 打开，四笔都可见，Original Transaction 是 A，R 的 Applies To 是 C。

这里特别要注意：I 和 C 都直接作用于 A，并不是按表格时间顺序逐笔相连。不能因为 I 排在 C 前面，就把 C 的 Applies To 填成 I。

### 8.4 授权完成后撤销

原型中还有一组 SGD 96.00 的预授权、SGD 88.00 的授权完成、SGD 88.00 的撤销。从撤销进入应看到三笔；撤销的 Applies To 指向授权完成，Original Transaction 指向预授权。

撤销保留自己的 Void 类型和结果，不把原完成记录从历史中删除，也不把撤销这一行改写成退款。

## 9. 查不到、没查全、查失败，要分别处理

### 9.1 确实没有其他关联记录

如果查询成功，当前笔没有其他可展示的关联记录，也没有允许披露的缺失引用：

- 弹窗只显示 `No related transactions found.`。
- 不展示只有自身一行的表格，不显示 1 transaction，也不显示 Original Transaction。
- 交易详情隐藏整个 Related Transactions 模块。

原型中的 `TXN-99882716105` 可用于检查这一情况。

### 9.2 知道有引用，但对应记录暂时不可用

例如，退款已经收到，原消费还没有补传；或者已有可信引用，但历史记录暂时查不到。这不等于“没有关联”。

如果只有当前笔可展示，显示关联记录暂不可用的提示；已知且允许披露的直接对象 ID 可以显示在提示里，不额外列一张只有自身的表。

如果还有其他已确认的关联记录，继续展示这些记录。对应的 Applies To 显示允许披露的引用和 Unavailable，不提供无效链接。

原记录后来补齐后，再次查询应能恢复正确关系，不要求用户手工指定原单。

### 9.3 关系冲突或历史范围不完整

遇到以下情况，不能为了凑出一组结果而猜：一个引用匹配到多笔记录、两种引用互相矛盾、引用形成循环，或者已知历史数据不完整。

已经确认的记录仍可展示，同时提示 `The relationship is incomplete. Only confirmed records are shown.`。无法确认的关系不强行连线；循环关系不能让查询卡住，也不能随意指定根交易。

如果只取得部分历史，要说明当前展示范围，不估算缺了多少笔，也不把当前查到的数量说成整个支付过程的完整数量。分页的“这一页只有 10 条”和历史数据的“本身没查全”必须区分。

### 9.4 正在加载

显示 `Loading related transactions…`。查询完成之前，不先闪现“没有关联”或 0 笔。当前笔的详情摘要保持可见；提示里若带编号，应使用对外展示的 Transaction ID。

### 9.5 查询失败

在当前关联区域显示加载失败提示和 Retry。点击 Retry 后重新查询当前笔，不切换到另一笔交易。

错误提示需要出现在用户实际能看见的滚动区域内，并获得焦点，不能藏在表格上方或被固定区域遮挡。若此前已有成功加载的内容，重试失败时保留这些内容，同时明确这次查询失败。

查询失败不能显示成“没有关联”，也不能把失败请求计入交易记录。

### 9.6 用户没有权限查看其中一些记录

关联功能沿用现有交易查看权限，不因为两笔有关系就扩大权限。记录内容、总笔数、Original Transaction、Applies To 和详情链接都要遵守同一权限范围。

服务端应在返回之前处理权限。不能先把整组数据交给浏览器，再靠前端隐藏。

没有权限查看的记录，不通过“还有 2 笔看不到”、隐藏记录的 ID 或原因提示泄露出来。前面关于“引用不可用”的展示规则，仅适用于用户被允许知晓的引用；不能拿它解释权限外的数据。

## 10. 研发接入时需要守住的规则

用户只看到表格，但后面的查询要支持从任意一笔查回整组，而不只是查这笔后面紧接着的成功操作。

| 需要保证的内容 | 具体含义 |
| --- | --- |
| 当前笔定位准确 | 列表、弹窗、详情都能定位同一条真实记录；对外 Transaction ID 和内部查询标识要对应正确 |
| 关系准确 | 能区分最初交易与每笔操作的直接对象；引用需要带上正确的账户、通道范围 |
| 结果准确 | 包含已形成记录的 Completed 和 Failed，不把处理中请求混进来 |
| 金额准确 | 保留每笔金额、币种、精度和业务含义，沿用正式产品的金额格式化能力 |
| 时间准确 | 取得真实时间及来源时区，统一转换后展示、排序，不能把本地时间直接标为 UTC |
| 数量和完整性准确 | 返回权限内可见总数，区分分页未加载与历史缺失；不能拿当前页条数冒充总数 |
| 不重复记账式展示 | 同一记录的重复通知不增加行数；实际发生的另一笔操作保留独立记录，即使金额相同 |
| 后来的数据能补齐 | 原单或后续记录迟到时，重新查询能更新关联过程 |
| 不影响原操作 | 只读关联查看与原退款、撤销等操作的金额计算保持各自口径 |

不在本 PRD 中指定必须新增哪张表或采用哪套接口。研发可以复用现有能力，但不能直接把原有“成功直接子交易”的结果当成这里需要的完整关联过程，也不能简单扩大旧查询范围而影响它的其他调用方。

## 11. 验收时逐项检查什么

以下是产品验收标准，不代表当前原型或生产系统已经全部通过。涉及真实权限、历史数据和接口的项目，需要在正式接入后验证。

| 编号 | 怎么检查 | 应看到的结果 |
| --- | --- | --- |
| RT-01 | 在 Completed、Failed 各选择一笔，打开 Actions | 两边都有 Related Transactions；其他操作的用途和可用条件保持原规则 |
| RT-02 | 点击 Related Transactions，再分别用关闭按钮、Esc、遮罩关闭 | 打开居中弹窗，菜单关闭；关闭后回到原 Actions，列表状态不丢失 |
| RT-03 | 对“消费加两次退款”，分别从三笔进入 | 都显示三笔，总数包含当前笔；Current 随入口变化 |
| RT-04 | 从失败退款进入有成功、失败记录的过程 | 两种结果都可见；失败退款的类型仍是退款 |
| RT-05 | 从预授权完成后的退款进入 | 能看到原预授权、增加、完成、退款；退款直接对象为完成记录，根交易为预授权 |
| RT-06 | 检查预授权增加与完成的关系 | 不按时间顺序误连；两者按来源记录分别指向正确对象 |
| RT-07 | 从撤销进入相关过程 | 撤销保持独立记录，直接对象正确，不删除或改写此前的完成记录 |
| RT-08 | 用日期、结果、类型、金额筛选找到入口，再查看关联 | 关联区不被原筛选和分页截断；列表结果、计数及导出范围不变 |
| RT-09 | 检查没有其他关联的交易 | 弹窗只有空态；详情隐藏模块；没有自身行和 1 transaction |
| RT-10 | 提供可披露的缺失原单引用，随后补齐原单 | 起初说明不可用而非没有关联；再次查询后显示正确关系 |
| RT-11 | 构造引用冲突、重复编号或循环 | 不随意匹配，不无限查询；保留可信内容并说明不完整 |
| RT-12 | 对同一记录重复上报，再加入一笔真实的新操作 | 重复通知不增加笔数，新操作保留独立记录 |
| RT-13 | 准备超过 10 笔的关联过程，入口选在后面的页 | 初次显示当前笔所在页；前后翻页、范围计数和 Locate current 正常 |
| RT-14 | 点击其他 Transaction ID、Applies To、Original Transaction | 进入正确详情顶部并出现切换提示；自身 ID 不可重复跳转 |
| RT-15 | 在详情间切换，再查看小票、刷新地址 | 金额、结果、字段、小票和 Current 都对应目标笔；不可用小票入口禁用 |
| RT-16 | 打开不存在或不可访问的交易地址 | 显示不可用并可返回列表，不回落到固定样例 |
| RT-17 | 从列表的后续页进入，连续切换详情后点击 Back | 原 Tab、筛选、日期、页码、每页条数及滚动位置恢复，不自动打开弹窗 |
| RT-18 | 直接打开详情，再点击 Back | 返回普通 Transactions 入口，不套用不存在的来源上下文 |
| RT-19 | 模拟慢请求、失败、Retry 成功和再次失败 | 加载不闪空态；错误可见且可聚焦；重试同一笔，已有内容不无故丢失 |
| RT-20 | 使用不同交易查看权限的账号查询 | 内容、计数、引用与链接均在权限内；不能据提示推断无权查看的记录 |
| RT-21 | 同卡号、同金额或同外部订单号但无引用；另准备可信的跨终端引用 | 前者不合组；后者在账户范围和权限允许时可关联 |
| RT-22 | 检查加载提示、错误提示、长 ID 和详情链接 | 只展示正确的 Transaction ID，内部记录键不冒充业务编号，长 ID 可读可选中 |
| RT-23 | 在桌面实际打开弹窗及详情，滚动长表格 | 表头紧凑、Current 清楚、按钮和分页可操作，内容不超出可用视口 |
| RT-24 | 同一笔分别从列表弹窗和详情查看，再检查原退款流程 | 两处关联内容一致；无新增整组金额汇总；原退款额度规则不受失败记录影响 |

## 12. 正式接入前还需要确认什么

这些是实施前需要核实的数据和接口问题，不是用户查看关联交易时要填写的新字段，也不表示本次增加功能范围。

| 事项 | 为什么需要确认 | 需要得到的结论 |
| --- | --- | --- |
| 支付引用与 ID 映射 | 不同来源的交易编号可能重复，内部记录键与对外编号用途不同 | 每个来源如何定位当前笔、直接对象和最初交易；在哪个账户、MID、通道范围内匹配 |
| 失败记录覆盖 | 现有成功子单查询未必能返回失败退款等记录 | 哪些类型的最终失败记录已保存，能否保留可信的原交易引用 |
| 历史数据覆盖 | 老记录不一定有完整引用，不能默认全部可回溯 | 可支持的历史范围、已知缺口以及用户可见的范围说明 |
| 真实权限规则 | 原型使用演示数据，没有接入服务端授权 | 各现有角色可以查看哪些交易；可披露引用的范围；计数和查询权限如何一致 |
| 时间来源 | 原型约定 UTC，真实数据可能包含不同来源时间 | 处理时间字段、来源时区及转换规则，确保 Time (UTC) 标注真实 |
| 金额含义 | 授权增加、小费调整等金额可能有各自含义 | 各交易类型的来源字段、单位、精度，展示时沿用哪套正式格式化能力 |
| 大组查询和分页 | 原型在浏览器内对完整演示集合分页 | 服务端如何返回总数、定位当前笔和稳定分页；基于实际规模确定性能目标，不编造时限 |
| 小票可用性 | 演示小票不能证明真实来源有对应小票 | 每笔真实记录如何确定可查看、可发送状态，切换后如何准确取到目标笔小票 |

当前还存在以下差异，实施和验收时要单独处理：

1. 关联组件的加载、失败提示目前会使用内部记录键，正式要求应改为对外 Transaction ID，或使用不带编号的提示。本文没有把这个原型问题当成需求保留。

4. 原型的新增记录保存在当前标签页会话中；分页基于浏览器里的演示集合，权限和时区也未接入真实来源。这些做法用于演示，不作为正式产品的实现要求。
