## 1. 业务背景与用户痛点

### 1.1 业务背景
Paywizard 支付管理平台服务于不同层级的机构（Service Provider、Agent、Merchant、Store）。在日常对账、客诉处理及商户资金核查中，操作员最频繁查看的模块就是 **Transactions（交易列表）** 与 **Transaction Details（交易详情）**。

当前交易列表是以**单笔流水（Transaction Record）**为单位平铺展示。这种单笔平铺的方式对于查看总体交易规模非常直观，但在处理“具有多次连续支付动作”的复杂交易时，存在严重的业务割裂。

### 1.2 核心业务痛点
1. **退款找原单难**：商户或客服查到一笔退款流水时，无法直接得知这是退给哪笔消费的；必须手动复制卡号、比对金额、猜测日期，反复搜索。
2. **多次退款难溯源**：同一笔消费可能发生多次部分退款，或者存在退款失败后再重试的情况。客服无法一览该消费一共发生过几次退款动作、每次退了多少、是否有失败记录。
3. **预授权全过程割裂**：在酒店、加油站、租车等预授权场景下，存在“预授权（Pre-Auth）→ 追加预授权（Incremental Auth）→ 授权完成（Auth Completion）→ 结算后退款（Refund）/撤销（Void）”等多次关联操作。各操作分散在不同日期、不同状态（甚至不同终端），操作员难以还原完整的资金链路。
4. **容易张冠李戴**：传统人工比对容易将同卡号、同金额但在不同时间发生的无关联独立交易错误归并，引发对账失误。

## 2. 业务目标与价值

通过在交易列表与交易详情中增加**关联交易（Related Transactions）**查看能力，达成以下业务目标：

- **找得到（入口触手可及）**：用户定位到关联链路中的**任意一笔**交易（无论消费、退款还是撤销），都可以直接打开完整的关联记录，无需先翻找原始交易。
- **看得懂（关系清晰准确）**：明确指出“当前看的是哪笔（Current）”、“整个链路最开始的交易是哪笔（Original Transaction）”、“当前这笔直接针对谁操作（Applies To）”，且每笔交易保留独立真实的金额与最终结果。
- **回得去（操作上下文零丢失）**：查完关联记录并跳转详情后，点击返回能够完整恢复列表的 Tab、筛选条件、页码和滚动位置，无需重新筛选。
- **降风险（不诱导错误对账）**：坚决不混淆支付关联与外部订单，坚决不进行无依据的金额汇总计算，确保数据严谨客观。

## 3. 需求边界与非目标（Non-Goals）

为了确保第一期聚焦核心价值、保障上线质量，特明确以下业务边界：

1. **按明确支付引用关联，不引入零售餐饮订单概念**：
   - 关联必须基于支付通道或系统底层具备明确父子引用关系的交易流水。
   - **同卡号、同金额、同外部订单号（External Order No）、同 RRN 均不单独作为关联依据**。不按商户的零售小票、餐饮台号归组。
2. **只读查看链路，不新增交易操作**：
   - 关联交易区域定位为“只读全貌视图”，不在此处新增快捷“发起退款”、“发起撤销”等业务动作按钮；原有操作仍严格在主列表 Actions 权限菜单中执行。
3. **不计算整组汇总金额**：
   - 首版不在关联区域展示“总支付”、“累计已退”、“剩余可退”或“净收款”等汇总指标。由于预授权、追加授权、失败退款等操作金额含义异构，跨币种无法折算，避免误导商户对账。
4. **不包含在途处理态（Pending）**：
   - 平台只沉淀最终确认记录，关联区仅展示 `Completed` 或 `Failed` 最终结果，不拉取或拼凑处理中的临时请求。
5. **不改变主列表流水形态**：
   - 主列表保持“一行一笔流水”，不进行前端行折叠或合流行展示，不改动主列表的统计计数与导出结果。
6. **仅限桌面端浏览器**：
   - 原型与正式 Portal 页面均基于桌面浏览器标准交互交付，不做手机端折叠适配。

## 4. 统一业务概念与定义规范

| 术语 | 英文标识 | 业务通俗定义 | 典型举例 |
| :--- | :--- | :--- | :--- |
| **当前交易** | **Current** | 用户当前正在查看或打开关联弹窗时选中的那笔基准交易。 | 用户在列表中对一笔退款 R 点击关联，R 即为 Current。 |
| **根交易 / 原始交易** | **Original Transaction** | 整个支付动作生命周期的最源头交易（通常为初始 Purchase 或初始 Pre-Authorization）。 | 预授权 A → 授权完成 C → 退款 R，Original Transaction 始终是 A。 |
| **直接作用对象** | **Applies To** | 这一行交易操作在业务逻辑上直接针对、修改的那一笔交易。 | 退款 R 是针对授权完成 C 发起的，R 的 Applies To 是 C（而非 A）。 |
| **关联交易全集** | **Related Transactions** | 从任意节点出发，通过显式父子支付引用拓扑扩展得出的、用户有权查看的所有祖先、同级、子孙交易集合。 | 消费 S、退款 R1、退款 R2 构成同一个关联全集。 |

> [!IMPORTANT]
> **区分 Original Transaction 与 Applies To**：
> 绝对不能简单把表格上一行当作下一行的直接对象！例如：在“预授权 A → 追加授权 I → 授权完成 C”链路中，I 和 C 都直接作用于 A。因此 C 的 Applies To 是 A，而不是时间排在它前面的 I。

## 5. 用户角色与数据权限隔离

关联交易严格继承 Paywizard 平台现有的组织层级与交易查看数据权限，**不因两笔交易存在关联关系而越权暴露数据**：

1. **机构层级隔离**：
   - **Service Provider**：仅可查看其所属体系内的关联交易；
   - **Agent**：仅可查看其代理商户管辖范围内的交易；
   - **Merchant**：仅可查看本商户 MID 范围内的关联交易；
   - **Store**：仅可查看当前门店终端所产生的交易。若退款发生在其他门店，且 Store 操作员无跨店查看权限，则权限外记录不可见。
2. **静默过滤原则（Silent Filtering）**：
   - 服务端必须在数据输出前完成权限脱敏与行级过滤。
   - 严禁向前端返回全量数据再由前端隐藏。
   - 对于用户无权查看的交易，界面上**严禁**出现“还有 2 笔无权查看”等泄露性提示，关联总笔数必须与用户实际可见笔数严格一致。
3. **缺失引用的合规展示**：
   - 若用户查看的退款交易本身带有原单编号引用，但该原单属于权限外或历史未接入数据，系统仅展示已知且被允许披露的交易编号并标记为 `Unavailable`，不提供详情跳转，不泄露该交易的具体金额与商户明细。

## 6. 详细功能与页面交互规范

### 6.1 交易列表页入口（`12.transaction_list.html`）

#### 6.1.1 操作入口定位与状态精简规则
- **Completed 交易 Actions**：包含 Action 分组（Transaction Details, Related Transactions, Send Receipt）与 Terminal 分组（Terminal Details 及可用后续退款/撤销操作）。
- **Failed 交易 Actions（严格精简）**：
  - 依据“界面只留必要内容”和“只显示当前状态允许的操作”规范，失败交易不生成小票、不具备终端重试或后续业务操作；
  - **失败交易的 Actions 菜单中严格仅保留两项功能**：
    1. `Transaction Details`（查看交易详情）
    2. `Related Transactions`（查看关联交易）
  - **彻底移除无关项**：不显示 `Send Receipt`（即使置灰也不展示）、不显示 `Terminal` 分组头、不显示 `Terminal Details`、不显示 `No follow-up transaction is available for this transaction type.` 提示文案，避免界面冗余干扰。
- **无前置门槛**：列表不需要预先异步查询每笔交易有没有关联，所有交易行均默认展示 `Related Transactions` 入口，点击后即时按需查询。

#### 6.1.2 居中弹窗（Modal Dialog）体验
- 点击 `Related Transactions` 后，自动收起 Actions 下拉菜单，并在屏幕中央弹出固定规格的模态对话框（标题：`Related Transactions`）。
- **关闭方式**：
  1. 点击弹窗右上角的关闭按钮（`×`）；
  2. 键盘按下 `Escape` 键；
  3. 点击弹窗外部半透明背景遮罩（Backdrop）。
- **焦点保护**：弹窗关闭后，页面焦点必须自动平滑恢复至原本所在那一行的 Actions 按钮上，主列表不发生意外刷新或跳动。

#### 6.1.3 与列表筛选条件的完全解耦
- 主列表的过滤条件（如日期范围选择“今天”、Tab 选择“Completed”、金额范围过滤）只用于帮助用户在列表中**定位入口交易**。
- **关联查询不继承主列表的筛选限制**：
  - 示例：商户在列表筛选“今天”并找到一笔退款，而原消费发生在昨天，打开关联弹窗时，**昨天的原消费必须完整显示**；
  - 示例：商户在“Completed”列表对原消费打开关联，关联的“Failed 退款”必须正常出现在弹窗内，绝不能被 Tab 截断；
  - 关联弹窗的打开与查看完全不会改变主列表的数据集、主列表分页以及主列表的批量导出范围。

### 6.2 关联交易表格展示规范（弹窗与详情通用）

弹窗与详情页共用一套高标准的关联交易表格组件（UI 对齐 PrimeVue 与紧凑规范）：

```
+-----------------------------------------------------------------------------------------+
| Related Transactions                                                                [X] |
+-----------------------------------------------------------------------------------------+
| 3 transactions                                  Original Transaction: 84607420342       |
+---------------------+-------------------+------------+-----------+--------------+-------+
| Time (UTC)          | Type              | Amount     | Result    | Applies To   | Tx ID |
+---------------------+-------------------+------------+-----------+--------------+-------+
| 2026-09-15 10:14:02 | Purchase          | GBP 48.60  | Completed | —            | ...42 |
| 2026-09-15 14:20:11 | Refund [Current]  | GBP 12.40  | Completed | 84607420342  | ...57 |
| 2026-09-16 09:05:30 | Refund            | GBP 5.00   | Completed | 84607420342  | ...61 |
+---------------------+-------------------+------------+-----------+--------------+-------+
| Showing 1-3 of 3 transactions                                                           |
+-----------------------------------------------------------------------------------------+
```

#### 6.2.1 顶部汇总信息栏
- **左侧总笔数**：明确显示当前可见集合的总交易数（如 `3 transactions`），总数**严格包含当前笔本身**。
- **右侧根交易定位**：如果系统能够确认最源头的根交易，显示 `Original Transaction: [ID]`；若根交易不是当前笔，该 ID 应提供可点击的超链接；若根交易就是当前笔，显示纯文本。

#### 6.2.2 字段列定义

| 列名 | 展示内容与规则 | 格式与行为要求 |
| :--- | :--- | :--- |
| **Time (UTC)** | 交易实际发生/处理的时间戳。 | 统一采用 UTC 时区标头与格式（`YYYY-MM-DD HH:mm:ss`），禁止混拼终端本地时间。 |
| **Type** | 交易类型真实名称（Purchase, Refund, Pre-Authorization, Auth Completion, Void 等）。 | 真实反映该笔操作本身的类型。**退款失败时，类型仍然是 Refund，严禁显示为 Failed**。当前笔在 Type 旁额外展示高亮标签 `Current`。 |
| **Amount** | 币种与交易金额（如 `GBP 12.40`、`USD 180.00`）。 | 保持该笔记录独立的币种与金额，不进行任何跨行累加或扣减。 |
| **Result** | 交易最终处理结果：`Completed` 或 `Failed`。 | 文字加语义色彩双重表达（Completed 采用绿系/深色文本，Failed 采用红系标签），符合无障碍标准。 |
| **Applies To** | 本笔交易直接作用的目标 Transaction ID。 | 根交易本身没有前置对象，固定显示 `—`；有明确作用对象且可见时提供详情跳转链接；若引用对象不可用则按异常规则显示。 |
| **Transaction ID** | 该笔交易在系统中对外公开的业务流水号。 | **当前笔（Current）显示为加粗普通文本，不可点击自身**；其他有权限查看的交易均渲染为可点击超链接，支持下划线交互。长 ID 支持文字换行与选中复制。 |

#### 6.2.3 视觉排版与分页
- **表格视觉规格**：严格执行项目既定标准，表头高度 `34px`、浅灰色背景、字体 `11px`，内容行等高紧凑排布。
- **当前笔高亮**：当前笔整行以浅蓝色背景（如 `#eef4ff` 或 `--brand-light`）高亮突出，并在打开后自动居中呈现给用户。
- **排序规则**：默认严格按 **Time (UTC) 从早到晚（正序）** 排列，完整还原资金与事件发生的时间线。
- **分页控制**：
  - 固定每页展示 `10` 条记录；
  - 超过 10 条时，表格下方显示分页控件：`Previous`、`Next`、`Locate current` 以及当前范围说明（`Showing 1-10 of 18 transactions`）；
  - 点击 `Locate current` 按钮，无论用户翻到第几页，均能瞬间切换回当前笔所在分页并使当前行可见；
  - 关联记录不超过 10 条时，完全隐藏分页控件，界面保持简洁。

### 6.3 交易详情页（`11.transaction_detail_redesign.html`）

#### 6.3.1 卡片布局位置
- 在交易详情页中，关联交易以独立卡片（Card）模块形式呈现，位于页面顶部**交易核心摘要（Amount / Status / Summary Cards）的正下方**、以及下方**技术扩展字段（Technical Sections）的正上方**。

#### 6.3.2 无关联时的优雅降噪（零干扰原则）
- 若经查询该交易确属单笔独立交易（既无父交易，也无子交易，关联总数 = 1）：
  - **在交易详情页中，必须将整个 `Related Transactions` 卡片模块彻底隐藏（Hidden）**；
  - 绝不展示一张只有当前交易自己孤零零一行的无意义表格，绝不干扰正常单笔交易的阅读体验。

#### 6.3.3 就地联动切换（In-Place Navigation）
- 当用户在详情页的关联表中点击另一笔交易的 Transaction ID 时：
  - **整页数据必须全部联动切换至目标交易**：包括顶部金额、状态标签、支付方式、终端信息、技术参数明细；
  - **关联表格内部状态联动更新**：目标交易在表格中自动切换为 `Current`（浅蓝底色与 Current Badge），原交易恢复为普通链接；
  - **小票能力同步联动**：根据目标交易是否具备小票数据，动态启用或禁用顶部的 `View Receipt` 与 `Send Receipt` 按钮；
  - **顶部滑出通知**：页面顶部主内容区中央滑出深色半透明提示条（Notification）：`Now viewing transaction [Target Transaction ID]`，停留约 3.2 秒后平滑收起，给用户明确的心理锚定。

### 6.4 列表上下文恢复与导航返回机制（Back 机制）

在多层级跳转穿透排查时，用户极其担心“回不去原本的列表位置”。系统必须严格保障返回上下文的无损恢复：

```
[列表页：第3页 / 筛选Failed / 滚动在中间]
     │ (点击某行 Actions -> Related Transactions -> 点击目标ID)
     ▼
[详情页 A] ──(关联表点击跳转)──> [详情页 B] ──(关联表点击跳转)──> [详情页 C]
                                                                │
     ┌──────────────────────────────────────────────────────────┘
     │ (点击顶部 Back 按钮)
     ▼
[列表页：完整恢复第3页 / 保持Failed / 筛选词仍在 / 滚动位置原地复原]
```

1. **上下文持久化范围**：
   - 包含：Completed 或 Failed Tab、已输入的搜索词、已选择的支付方式/通道、日期起止范围、筛选面板展开状态、当前页码（Page Index）、每页条数（Page Size）、表格横向与纵向滚动条像素位置。
2. **多层穿透后的返回行为**：
   - 用户从列表进入详情页 A，又从 A 的关联表跳转到详情页 B，再跳转到详情页 C。
   - 在详情页 C 点击顶部的 **Back** 按钮时，**直接回到最初进入前的列表状态**，而非一步一步倒退回 B 和 A。
   - 返回列表后，不需要自动重新弹出关联弹窗，保持列表整洁。
3. **直接访问 URL 的保底机制**：
   - 如果用户是通过外部链接或收藏夹直接打开详情页（URL 无前置列表上下文标记），点击 Back 按钮平滑导航至交易列表默认页，不引发报错。

## 7. 典型业务场景与用例矩阵

以下场景及编号用于业务评审与测试用例设计，涵盖所有典型支付交易组合：

### 场景 1：一笔正常消费 + 两次部分退款（Partial Refunds）
- **业务流程**：商户发生一笔 GBP 48.60 的消费（S），顾客在不同时间分别退款 GBP 12.40（R1）与 GBP 5.00（R2）。
- **展示表现**：
  - 无论从 S、R1 还是 R2 进入，关联表均展示全部 3 笔流水；
  - 顶部 Original Transaction 标记为 S；
  - R1 和 R2 的 Applies To 均明确指向 S；
  - 若从 R2 打开，R2 行高亮且标注 Current。

### 场景 2：消费 + 退款失败 + 退款重试成功
- **业务流程**：消费 S（USD 3.50），商户尝试退款 USD 1.00 失败（R_fail），随后重新退款 USD 1.00 成功（R_succ）。
- **展示表现**：
  - 在 Failed 列表找到 R_fail 并打开关联，3 笔记录全部呈现；
  - R_fail 行显示 Type: `Refund`，Result: `Failed`；
  - R_succ 行显示 Type: `Refund`，Result: `Completed`；
  - 两者均指向 S，清楚反映操作失败历史与后续补救情况，杜绝重复退款纠纷。

### 场景 3：预授权全生命周期（酒店/租车场景）
- **业务流程**：
  1. 顾客入住：发起预授权 A（USD 180.00）；
  2. 延长住宿：发起追加预授权 I（USD 45.00），直接指向 A；
  3. 离店结账：发起授权完成 C（USD 212.50），直接指向 A；
  4. 账单纠错：对结算扣款发起退款 R（USD 32.50），直接指向 C。
- **展示表现**：
  - 4 笔按发生时间正序排列：A → I → C → R；
  - 顶部 Original Transaction 明确为 A；
  - **关键关系校验**：I 和 C 的 Applies To 均为 A；R 的 Applies To 为 C。绝不按行顺序将 C 误标为指向 I。

### 场景 4：预授权完成后的撤销（Void）
- **业务流程**：预授权 A → 授权完成 C → 当日发现扣款错误立即发起撤销 V。
- **展示表现**：
  - 展示 3 笔流水，V 的 Type 为 `Void`，Applies To 指向 C；
  - 撤销操作不会将完成记录 C 从历史中抹除，也不会把 C 改写为退款，如实还原撤销事件。

### 场景 5：跨终端支付关联
- **业务流程**：顾客在 01 号自助机消费，因设备故障，收银员在 02 号人工收银台为其办理退款（同一商户同一通道）。
- **展示表现**：
  - 只要两笔交易在底层具备可靠支付引用，且操作员有权查看两台终端，两笔交易正常归并展示；
  - 终端不同不阻断合法支付关联的展示。

## 8. 异常边界与错误处理规范

| 异常场景 | 业务现象与原因 | 列表弹窗表现 | 交易详情页表现 |
| :--- | :--- | :--- | :--- |
| **单笔独立无关联** | 该交易无任何父子流水，关联总数 = 1。 | 居中展示空态说明：<br>`No related transactions found.`<br>不展示只有一行的无意义表格。 | **整个 Related Transactions 卡片自动完全隐藏**，不占页面版面。 |
| **原单未补传或历史丢失** | 交易本身（如退款）包含父单号，但原单记录暂未入库或丢失。 | 提示：<br>`Related records are unavailable. Applies To: [ID].`<br>保留已知引用，不强行组装空表。 | 提示关联记录暂不可用，标出可披露的前置引用编号。 |
| **关系冲突或循环引用** | 数据源存在矛盾引用或环状依赖。 | 顶部警示条提示：<br>`The relationship is incomplete. Only confirmed records are shown.`<br>仅展示已校验安全的分支，避免卡死。 | 同左。 |
| **查询中（Loading）** | 网络请求耗时。 | 友好提示：<br>`Loading related transactions…`<br>不闪烁 0 条或错误态。 | 同左，骨架或 Loading 提示保持在卡片内部。 |
| **网络故障或服务异常** | 接口报错或超时。 | 提示加载失败并提供 `Retry`（重试）按钮；错误提示自动获得焦点。 | 同左；若之前已加载成功过部分内容，重试期间不白屏清空。 |

## 9. 业务红线与禁区（Guardrails）

为避免产生业务争议，以下事项列入需求红线，研发与测试必须严格恪守：

1. 🚫 **严禁私自累计或汇总金额**：任何页面不得私自计算诸如“总付款金额”、“累计已退金额”或“账户净额”。不同交易类型（预授权 vs 完成 vs 退款）的金额含义不同，且失败记录有金额但未扣款，随意汇总必定导致财务理解歧义。
2. 🚫 **严禁根据非唯一标识聚类**：严禁仅凭相同卡号、相同金额、相同日期或外部订单号自动合成关联交易。
3. 🚫 **严禁以状态代替类型**：退款失败时，类型必须是 `Refund`，结果是 `Failed`。绝不能将 Type 篡改为 `Failed`。
4. 🚫 **严禁干扰原有退款业务逻辑**：关联交易纯属前台信息查看视图，原系统对单笔消费“还能退多少钱”的校验必须继续沿用后台原有支付通道的配额规则，不得受关联视图中出现的失败记录干扰。

## 10. 研发提测与 QA 验收清单（Checklist）

测试与业务验收时，逐项核对以下 20 项验收标准（Acceptance Criteria）：

- [ ] **AC-01 列表入口覆盖与失败交易精简**：
  - 在 `Completed` 列表，每行 Actions 菜单完整展示 Transaction Details, Related Transactions, Send Receipt, Terminal Details 及可用后续操作；
  - 在 `Failed` 列表，每行 Actions 菜单**严格仅保留** `Transaction Details` 与 `Related Transactions` 两个可用功能，不展示 Send Receipt、Terminal 分组及无后续交易提示。
- [ ] **AC-02 弹窗交互规范**：点击入口平滑弹出居中对话框；支持右上角 `×`、键盘 `Escape`、点击遮罩关闭；关闭后焦点精准恢复到原行的 Actions 按钮。
- [ ] **AC-03 双向穿透完整性**：对于同一组关联流水，无论从最初消费进入、中间授权进入、还是末端退款进入，查出的关联交易成员总集完全一致。
- [ ] **AC-04 当前笔精准识别**：当前入口交易在表格中整行浅蓝高亮，Type 旁显示 `Current` 徽标，其 Transaction ID 为普通文字且不可点击。
- [ ] **AC-05 跨状态与跨日期穿透**：列表即便筛选了特定日期或特定状态，弹窗查询均能穿透展示不同日期、不同状态的合法关联单。
- [ ] **AC-06 根交易定位**：能正确识别并展示 `Original Transaction: [ID]`；若根交易不是当前笔，该 ID 点击可跳转详情。
- [ ] **AC-07 直接对象（Applies To）准确性**：严格反映每笔操作的直接对象（如撤销指向完成，完成指向预授权），不按行顺序机械串联。
- [ ] **AC-08 紧凑表格规格**：表格执行 `34px` 浅灰表头、`11px` 规范字体，在视口内具备独立滚动条，长 ID 换行整齐可选中复制。
- [ ] **AC-09 超过 10 条稳定分页**：超过 10 条展示分页器；点击 `Locate current` 可从任意分页一键返回当前笔所在页并高亮显示。
- [ ] **AC-10 详情页卡片位置**：详情页中关联卡片准确位于顶部摘要下方、技术字段上方。
- [ ] **AC-11 详情页就地切换**：在详情页关联表点击其他 ID，整页数据立即切换至新交易，顶部滑出约 3.2 秒提示条，自身 ID 不可重复点击。
- [ ] **AC-12 详情页小票联动**：切换至新交易后，顶部 `View Receipt` 和 `Send Receipt` 按钮根据目标交易实际小票可用性动态启用或禁用。
- [ ] **AC-13 无关联彻底隐藏**：对于无任何关联的独立单笔交易，列表弹窗展示无关联提示，详情页彻底隐藏整块关联卡片。
- [ ] **AC-14 列表上下文无损恢复**：从列表进入详情并连续跳转多笔关联后，点击 Back 按钮完整恢复初始列表的 Tab、筛选词、页码及滚动条位置。
- [ ] **AC-15 直接访问容错**：无上下文参数直接打开详情页，点击 Back 安全返回交易列表默认页。
- [ ] **AC-16 加载态与重试可用**：模拟弱网能看到加载提示；模拟接口报错显示错误提示与 Retry 按钮，重试在原处生效。
- [ ] **AC-17 权限严格静默过滤**：无权查看的交易直接从列表中剔除，总笔数相应扣减，界面不透露“由于权限隐藏 X 笔”等敏感线索。
- [ ] **AC-18 跨终端关联支持**：同一商户同一通道下，不同终端发生的消费与退款只要引用合规，能够正常关联。
- [ ] **AC-19 无金额汇总泄露**：弹窗与详情关联区任何角落均不出现多笔交易相加后的合计金额字段。
- [ ] **AC-20 时间统一 UTC**：表格统一采用 UTC 标头与格式，时间排序严格按正序展示。

## 11. 业务待确认事项（Open Questions for Alignment）

以下问题由产品负责人与业务方在评审会上敲定：

1. **跨门店退款在门店角色的可见性约定**：
   - *问题*：若总店在 A 门店消费，后续在 B 门店退款。当 B 门店操作员（仅有 B 店权限）查看这笔退款时，是否允许在关联表中看到 A 门店的原消费流水？
   - *建议倾向*：遵循权限第一原则。若门店角色严禁跨店，则原消费显示为 `Unavailable (跨门店记录无权查看详情)`，退款的 Applies To 仅保留可披露的交易 ID 文本，不可点击穿透进入 A 店详情。
2. **是否需要展示退款原因（Refund Reason）**：
   - *问题*：目前表格中包含 Time, Type, Amount, Result, Applies To, Transaction ID，部分商户反馈希望直接看到退款原因（如“客户退货”、“重复扣款”）。
   - *建议倾向*：首版保持 6 列紧凑格局，避免撑宽表格导致水平滚动。退款原因作为次级信息，可在点击进入退款详情后在技术明细中查看；二期视高频反馈再评估是否加入主列。
