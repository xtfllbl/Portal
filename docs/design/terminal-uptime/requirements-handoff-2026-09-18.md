4. 旧稿仍有手机验收要求；与最新桌面范围冲突。

8. 单终端摘要目前会过滤无结果日期；带 S/N 的矩阵保留七列。用户本轮已确认摘要也固定七格，接入前显示不可点击的 Not enrolled。最终需求应明确此处为待研发实现的原型差异。

## 生产接入缺口

| 缺口 | 研发文档需要明确的边界 |
| --- | --- |
| 真实心跳与 Online 覆盖 | 原型仅有模拟的有界状态区间，没有真实心跳事件；需独立提供有效心跳发生时间和 Online 覆盖。昨天心跳的覆盖延续到午夜后，不代表今天收到过心跳。 |
| 判定参数 | 每三分钟一次心跳，孤立一次漏报不扣在线率；第二次连续漏报后回溯至第一次应到时刻计 Offline，直到有效心跳恢复。已定产品规则不能以技术待定为由重新解释。 |
| 统计截止 | 请求时间、数据更新时间、数据完整截止时间在生产可能不同；需确定延迟时如何截断统计，不能无限延长旧 Online。 |
| 迟到与纠正 | 保留范围内允许权威数据修正，但接收窗口、重算时效、版本与审计保留期限尚未落实。 |
| 身份与权限 | URL scope、演示角色和前端过滤不构成生产授权；后端必须裁剪门店归属时间片并复核管理权限。 |
| 初始化与容量 | 首次上线的可用历史起点、权威归属历史、数据规模和响应目标需评审确认；不能补造不存在的历史。 |

## 本轮决策树

```text
研发文档
├─ 已有产品规则：沿用已确认的最新记录，无需重新确认
├─ Q1 交付范围：完整闭环 [已确认]
├─ Q2 心跳周期：每三分钟一次 [用户明确]
│  └─ Q3 容错：允许一次漏报，不计离线 [已确认]
│     └─ Q5 连续漏报：第二次确认后回溯至第一次缺报，直到恢复 [已确认]
└─ Q4 摘要不足七天：固定七格并标记原因 [已确认]
```

Q1 用户选择完整闭环：矩阵、摘要、单日详情和营业时间。
Q2 用户原话：“这个因为现在是明确的,终端每3分钟会心跳一次,告诉系统自己活着”。此答复确定发送周期，未确定迟到宽限和数据修正流程；不能解读为其他未决参数一并批准。
Q3 用户原话：“这种其实可以计入误差,1次漏报完全可以接受”。因此不采用之前的三分钟无宽限建议。08:00 收到、08:03 漏报、08:06 收到的场景不扣在线率。
Q4 用户回答“接受”：摘要保留七格，与矩阵一致；接入前显示不可点击的 Not enrolled。此项只纳入本次文档，用户没有要求本轮修改原型代码。
Q5 用户明确否定“不回溯”的建议，原话：“不符合,我可以宽限一次,但是第二次又没收到,那第一次没收到的窗口也要计入离线,直到恢复”。最终规则：08:00 收到、08:03 漏报、08:06 仍未收到、08:09 恢复，则 Offline 为 08:03–08:09，共六分钟；08:06 是确认时刻，08:03 是离线起点。08:04 查看时尚处容错的暂计值，可在 08:06 判定后被回溯修正。恰好 08:06 收到则仍是可容忍的一次漏报，不产生 Offline。

本轮产品分支已收敛；真实时间字段、采集延迟、迟到纠正、授权映射、历史起点和容量目标作为研发评审的技术契约落实，不冒充已接通能力。该口径已经纳入 ADR 0014、领域术语和正式需求，正式需求包含 41 项验收案例。未修改页面脚本，未发布 GitHub Issue。

精度约束：可以保留心跳时间戳和状态边界的秒级精度，但仅凭三分钟心跳不能识别心跳间所有短暂中断；如需识别，必须有额外的权威连接事件。最终需求不能把显示精度写成实际故障检测精度。
