# 厂商测试卡系统设计基线

日期：2026-10-21。状态：业务决定已逐项确认；静态原型及第二轮卡列表标题、卡详情结构和取消交易详情的修正已实施并完成桌面验证。真实交易服务尚未接入。

## 目标与边界

服务自助机厂商的调试和出厂测试。终端来自 TMS 同步的厂商终端列表，无须创建生产服务商、商户、门店或执行生产终端绑定流程。

- 发卡时的适用厂商为顶层 UPT Partner；下级实体不单独成为可授权厂商，PSP 及其下级不作为发卡授权对象。此限制针对厂商选择，不因测试终端当前流转到某贸易商而结束测试资格。
- 运维人员负责开卡、管理和余额调整。厂商在终端使用卡片，本期不增加厂商自助管理入口。
- 终端只要曾在厂商库存出现过，且从未绑定任一门店，就仍处于测试阶段；当前位于哪个贸易商不影响测试资格。不得增加“仅厂商直属库存”或“转给贸易商即停止”的限制。
- 同一终端曾进入 A、B 两家厂商库存时，以最近一次厂商归属为准，仅接受该厂商的测试卡；普通贸易商间流转不改变厂商归属。
- 首次绑定任一门店即结束出厂测试资格。后续解绑也不自动恢复测试资格。
- 测试卡业务独立于正式交易系统，测试交易有专属查询页面，不计入正式营业额和经营统计。复用已有能力不等于共享生产交易记录；具体部署与存储方案未决定。
- 测试余额为额度，无须实际付款充值。消费真实扣减测试额度并触发出货，不形成厂商应收或结算款。

| 功能 | 已确认要求 |

| Balance Adjustment | 保留余额增加和扣减能力。 |
| Transactions | 新增专属页面，供运维查询厂商测试交易，与现有正式 Transactions 页面独立。仅做列表查询，不提供交易详情页或发起消费、退款、撤销、冲正等交易的后台操作；本期不额外增加交易导出。卡导出已单独确认保留。 |
| 交易能力 | 复用现有储值卡已支持的金融交易类型，不额外排除其中已有的退款、冲正；继续遵守原交易关联和厂商隔离规则。不据当前原型的 Sale 示例推定后台完整支持清单。 |
| 丢失换卡 | 本期不提供。 |

## 卡列表与卡详情

- 卡列表列：UID／显示卡号、适用厂商、余额／币种、状态、最后交易时间、交易次数、操作。
- 卡列表筛选：卡号、厂商、状态、余额；移除持卡人、联系方式、生产 Group／Store 筛选。
- 列表删除持卡人列及 Rule 列；不保留单次使用、月／日限额或 Weekdays 等旧规则展示。
- 卡详情保留 General、History、Transactions，分别用于编辑基本信息、查看变更与余额调整记录、查询该卡交易。
- 卡片的交易入口统一指向 Test Cards 交易页面并带入当前卡的查询条件，不跳往正式 Transactions。
- 所有卡列表、详情及相关流程均移除换卡入口。

## 基础校验

- 一卡一币种，交易币种必须与卡币种一致。
- 余额不足时拒绝消费；手工扣减也不得使余额为负。
- 保留激活时间和可选到期时间及其原有校验；未填写到期时间即长期有效。
- 卡状态及其他基础规则继续沿用储值卡已有规则；本设计中已明确删除或替换的规则除外。
- 厂商隔离、终端测试资格和历史交易归属是独立业务约束，不能由前端隐藏按钮或下拉选项代替实际受理校验。

## 测试交易查询

- 筛选：日期、厂商、卡号、终端 S/N、交易类型、交易结果。
- 列表：交易时间、交易号、厂商、卡号、终端 S/N、交易类型、金额／币种、交易结果。
- 成功和失败交易均可查询，结果沿用 Completed／Failed，不将仍处理中请求混入最终交易记录。
- 交易查询止于列表，不提供交易详情页面；交易号不再作为详情链接。卡详情内的 Transactions 页签遵循相同规则。
- 展示交易发生时的厂商，不因卡片或终端后续变更而改写历史归属。

## 验收场景

| 场景 | 预期 |
| --- | --- |
| A 厂商卡在归属 A、从未绑定门店的终端消费 | 其他卡规则满足时允许，扣减测试额度并触发出货。 |
| 同一终端转给贸易商，未绑定过门店 | 仍接受 A 厂商测试卡，不因当前贸易商改变而停止。 |
| 同一终端后来进入 B 厂商库存 | 仅接受 B 厂商卡；贸易商间流转不触发该厂商变更。 |
| 终端首次绑定任一门店，随后解绑 | 绑定起结束厂商测试资格，解绑不自动恢复。 |
| 卡片适用厂商由 A 修改为 B | 保存后立即按 B 受理；卡号、币种、余额保留，A 历史交易仍归 A 且仅可查询。 |
| 跨厂商卡消费，或改换厂商后处理旧厂商交易 | 拒绝；不能通过退款、撤销等后续操作绕过厂商隔离。 |
| 币种不匹配、消费余额不足、手工扣减后为负 | 拒绝操作，展示原因并保留输入。 |
| 单卡和批量开卡 | 均单选一家厂商，均不出现已删除的持卡人、限额及生产范围字段。 |
| 查询测试成功／失败交易 | 可按已确认条件筛选，展示交易发生时厂商；交易号为普通文本，无交易详情入口和发起金融交易的操作。 |
| 查询正式卡／正式交易及经营统计 | 不混入测试卡业务数据；原正式卡流程继续按其既有规则运行。 |

页面遵循 [UI 规范](ui-standard.md)，复用静态 HTML／CSS／JavaScript 架构及共享 Portal 样式。此前桌面页面与本地交互验证见[实施与验证记录](../validation/test-card/README.md)，第二轮修正已补充对应的页面与交互验证。浏览器本地卡管理、余额变更和演示交易查询不代表真实交易、TMS 同步或后台授权已完成；服务端仍需实现相同的受理规则。系统部署、服务端存储和后端协议属于开发评审事项。

## 现有原型事实

- Partner 仅顶层保存 UPT/PSP 类型，下级继承展示根类型；顶层 Terminal List 汇总自身及后代终端。UPT 标签本身不足以证明一个下级实体是独立厂商。依据：`26.partner_information.html` 的 `getPartnerStyle`、`isUptRootPartner` 和终端范围逻辑。
- Maintain 现有 Prepaid Cards 仅开放 Card List 及详情，其开卡、调额、换卡路由另有限制。TEST CARD 需要独立的菜单和业务路径。依据：`scripts/platform-admin-shell.js`。
- 当前卡详情有 General、History、Transactions；交易仅为 Sale 示例，不足以验证真实金融交易类型清单。导入、导出交互也不等于后端能力已经完成。依据：`19.prepaid_card_detail.html`、`15.prepaid_card_activation.html`、`scripts/prepaid-cards.js`。
- 新增／详情卡表单没有星期选择或每日使用时间窗；列表中的 `Daily $50 / Weekdays` 仅为静态 Rule 示例，不应由此引入新的时段配置。有效期已确认保留，其余原有基础字段为 Card Type、Physical Type、UID、Display Card Number、Currency、Initial／Current Balance、Status、Activation Date。

独立业务边界见 [ADR-0017](../adr/0017-separate-manufacturer-test-card-business.md)。
